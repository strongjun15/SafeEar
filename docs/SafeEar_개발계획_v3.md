## 0. 설계 대원칙

이 프로젝트의 모든 설계 판단은 아래 세 원칙에서 파생된다.

### 원칙 1 — 측정과 해석의 분리

> **측정·계산 경로에는 학습 모델을 넣지 않는다. AI는 해석·예측·개인화 레이어에만 배치한다.**

이 앱의 최대 강점은 화면에 뜨는 숫자를 국제표준과 피어리뷰 논문으로 한 줄씩 역추적할 수 있다는 점이다. 신호처리 경로에 블랙박스 모델이 들어가면 "그 숫자가 왜 그렇게 나왔는가"에 답할 수 없게 되고, 축적한 문헌 근거가 통째로 무의미해진다.

따라서 AI는 표준이 **답하지 못하는 영역** — "이 사용자가 앞으로 어떻게 될 것인가" — 에만 사용한다.

### 원칙 2 — 관찰은 단언하고, 원인은 단언하지 않는다

앱은 의료기기가 아니며 난청을 진단할 수 없다. 교정되지 않은 이어폰으로는 절대 역치(dB HL)를 알 수 없다.

| 금지 | 허용 |
|---|---|
| "소음성 난청이 감지되었습니다" | "3주간 같은 콘텐츠에서 볼륨을 올리는 패턴이 관찰됩니다" |
| "당신의 4kHz 역치는 25 dB입니다" | "첫 주 대비 이 대역의 상대 변화가 큽니다" |
| "안전합니다" | "이번 주 허용 선량의 39%를 사용했습니다" |

WHO-ITU 문서 자체가 선량 추정의 불확실성 때문에 사용자에게 "안전" 또는 "위험 없음"을 단정하지 말 것을 권고하고 있다.

### 원칙 3 — 절대 판정보다 상대 비교

교정 문제로 절대 SPL 추정에 큰 불확실성이 있으므로, 가능한 모든 지표를 **동일 사용자·동일 기기 내의 상대 비교**로 설계한다. 이는 한계를 인정하는 후퇴가 아니라, 근거가 허용하는 범위에서만 주장하는 설계 규율이다.

## 1. 문제 정의

### 1.1 왜 소프트웨어가 필요한가

소음성 난청(NIHL)이 위험한 이유는 손상의 크기가 아니라 성질에 있다.

- **비가역성** — 유모세포는 재생되지 않는다
- **무통성** — 달팽이관에는 통각 수용체가 없다
- **누적성** — 하루의 노출은 무해해도 10년의 노출은 유해하다

일반적인 신체 손상은 통증이라는 피드백 루프를 가지지만 청각은 이 루프가 구조적으로 없다. "귀가 먹먹하다"고 느낄 때는 이미 일시적 역치변동(TTS)이 발생한 뒤이고, "잘 안 들린다"고 느낄 때는 영구적 역치변동이 축적된 뒤다.

**→ 신체가 제공하지 않는 피드백 루프를 소프트웨어가 대신 만든다.** 이것이 프로젝트의 한 줄 정의다.

### 1.2 기존 시스템이 버리는 네 가지 정보

Apple(iOS 14.2~), Samsung(Volume Monitor), Google(Android 14 Computed Sound Dose)은 모두 이어폰 노출량 모니터링을 이미 탑재하고 있다. 문제는 세 플랫폼이 동일한 하나의 가정 위에 서 있다는 점이다.

**등가 에너지 가설(EEH)**: "소리 레벨 × 시간, 즉 총 음향 에너지가 같으면 손상도 같다"

WHO-ITU H.870과 IEC 62368-1이 채택한 이 표준은 A-가중 음압의 제곱을 시간 적분한 단일 스칼라(Pa²h)로 위험을 표현한다. 이 압축 과정에서 다음이 버려진다.

| 버려지는 정보 | 결과 |
|---|---|
| ① 소리의 시간 구조 (첨도) | 뾰족한 소리와 평평한 소리를 구분 못 함 |
| ② 휴식 (회복 동역학) | 쉬어도 게이지가 내려가지 않음 |
| ③ 주파수 분포 (토노토피) | 어느 대역이 위험한지 숨김 |
| ④ 미래 | 사후 통보만, 사전 예측 없음 |

본 프로젝트는 이 네 가지 정보 손실을 복원하는 것을 문제로 설정한다.

### 1.3 왜 청소년인가

- 2017년 대한이비인후과학회·대한이과학회 전국 중·고등학교 110개교 3,013명 측정: 고1의 16.5%가 WHO 기준 정상 청력(15 dB)을 벗어남, 9.0%에서 소음성 역치변동(NITS) 관찰. 중1은 각각 17.9%, 10.4%
- 서울대병원 오승하·서울대 의대 홍윤철 교수팀, 중고등학생 2,879명 대상 정밀 청력검사·어음청력검사 결과 **17.2%가 소음성난청** (PLOS ONE 게재, 동아사이언스 2019.10.17 보도). 서로 다른 두 조사에서 16~17%대가 일관되게 관찰된다
- 이 조사는 **무선 이어폰 대중화 이전**에 이루어졌다
- 한국갤럽 2024년 7월: 국내 무선 이어폰 사용률 59%, 20~30대는 80% 안팎
- Apple Hearing Study(2021): 참가자 10%가 주간 헤드폰 노출 WHO 한계 초과

**→ 모니터링 기능이 이미 탑재되어 있음에도 초과 노출이 지속된다는 사실 자체가 본 연구의 동기다.**

또한 Apple이 2024년 이후 AirPods Pro에 추가한 순음청력검사·보청 기능은 **만 18세 이상 대상**이어서, 예방 효용이 가장 큰 청소년이 구조적으로 제외되어 있다.

## 3. 핵심 계산: 위험도는 어떻게 산출되는가

### 3.1 1단계 — 프레임별 원시값 추출

1초 프레임마다 두 가지를 계산한다.

**(가) A-가중 에너지**

```
E_frame = mean( p_A(t)² )     [Pa²]
```

**(나) 첨도 β**

```
β = E[(x − μ)⁴] / σ⁴
```

가우시안 소음에서 β = 3.

**근거**: A-가중은 ISO 226 등청감곡선에서 유도된다.

> **한계 명시**: ISO 226의 정규 등청감곡선은 **18세 이상 25세 이하** 이과학적 정상인의 평균 판단으로 정의된다(2023년 개정판도 동일). 즉 A-가중 자체가 젊은 성인 전용 곡선이며, 또한 약 40폰의 낮은 음량에서 유도되어 크고 충격적인 음악 피크에 그대로 적용하는 것이 타당한지에 대한 문제 제기가 존재한다.
>
> 부수적으로, 본 앱의 주 사용자층(10대)은 ISO 226의 연령 범위에 근접하므로 이 한계가 상대적으로 작게 작용한다.

### 3.2 2단계 — 첨도에 의한 시간축 보정

**핵심 개념: 첨도 보정은 소리를 더 크게 치는 것이 아니라, 노출 시간을 늘려 무는 방식이다.**

Zhao 등(2010)이 제안하고 Xie 등(2016)이 사용한 형태:

```
CNE' = CNE + [ (ln β + 1.9) / log 2 ] × (보정항)
```

이 형태가 선택된 이유는 가우시안 소음(β=3)에서 `[(ln β + 1.9)/log 2]`가 10에 가까워져, **보정 CNE가 원래 CNE와 같아지도록** 설계되었기 때문이다. 즉 평평한 소리에서는 보정이 자동으로 무효화된다.

Goley 등(2011)은 대신 LAeq를 직접 보정하는 방식을 제안했고, 여기에는 양의 상수 λ가 들어간다. 최근 연구에서 최적 첨도 보정계수는 **6.5**로 추정되었다.

**동작 예시**: 게임 총소리로 β = 9인 1초 프레임 → 계수 약 2 → **이 1초를 2초로 계산**

**근거 문헌**

| 문헌 | 기여 |
|---|---|
| Goley, Song, Kim (2011) | 첨도 보정 음압 레벨의 원형, 본 연구 계수의 1차 출처 |
| Zhao et al. (2010) | 방직·금속가공 노동자, 첨도 보정 CNE 최초 검증 |
| Xie et al. (2016) | 제철소·방직공장 노동자 341명(가우시안 163 / 복합 178) |
| Shi et al. (2022) | 5개 산업 제조업 노동자 1,558명, 대규모 재검증 |
| Zhang et al. (2022) | 첨도 보정계수 6.5 도출 |
| Qiu, Hamernik et al. | 동물 실험 + 노동자 역학 결합, 첨도 지표 유효성 입증 |

**생리학적 기전**: 등골근 반사는 반응 지연이 있고 2 kHz 이하에서만 유의하게 감쇠시키므로, 짧고 뾰족한 고주파 에너지는 이 보호 기제를 우회해 달팽이관에 그대로 전달된다.

**체계적 문헌고찰**: 복합 소음의 경우 ISO 1999가 영구역치이동을 평균 약 13.6 dB 과소평가한다는 결과가 보고되었다.

> **한계 명시**: 위 연구들의 대상은 대부분 총성·프레스 같은 산업 충격 소음과 동물 모델이다. 음악은 크레스트 팩터가 높으나 총성 수준의 충격은 아니므로, 본 연구는 첨도 보정을 **확정된 임상 위험이 아니라 상대적 가중치**로 제시한다.

> ⚠ **v3 검토 메모 — 보정식 형태를 하나로 정리해야 한다 (9절 #6, #7, #8)**
>
> 이 절에는 성격이 다른 두 보정식이 섞여 있다. 아래 내용은 원문 논문과 대조해 확정해야 한다.
>
> **(가) Zhao·Xie형 — 노출 연수에 거는 보정**
> ```
> CNE  = L_Aeq + 10·log₁₀(T)                    T = 노출 연수
> CNE' = L_Aeq + [(ln β + 1.9) / log₁₀2]·log₁₀(T)
> ```
> β = 3이면 대괄호 안이 (1.0986 + 1.9)/0.301 ≈ 9.96 ≈ 10이 되어 원래 CNE와 같아진다. 위에 적힌 "CNE + … × (보정항)" 표기는 이 식을 옮기다 흐트러진 것으로 보인다. 이 식은 **수년 단위 누적 노출**용이라 1초 프레임에 바로 쓰기 어렵다.
>
> **(나) Goley·Zhang형 — 레벨에 dB를 더하는 보정**
> ```
> L'_Aeq = L_Aeq + λ·log₁₀(β/3)          λ = 6.5 (Zhang 2022)
> 에너지 배율 w(β) = 10^(λ·log₁₀(β/3)/10) = (β/3)^(λ/10)
> ```
> β = 9, λ = 6.5 → w ≈ 2.04. **위의 "1초를 2초로 계산" 예시는 (나)형의 결과와 일치한다.** 1초 프레임마다 선량에 배율을 곱하는 이 앱의 구현에는 (나)형이 자연스럽다.
>
> **추가로 정할 것**
> - **β 계산 창 길이**: 첨도 문헌은 보통 40초 단위 창으로 β를 구해 평균한다(원문 확인 필요). 1초 창으로 구한 β는 분포가 달라지므로 40초 이동창을 쓸지, 1초 창을 쓰고 한계로 적을지 결정한다.
> - **β < 3 처리**: 사인파처럼 평평한 신호는 β ≈ 1.5이고, 이때 w < 1이 되어 등에너지 선량보다 **낮게** 계산된다. 문헌 근거가 주로 β ≥ 3 영역이므로 하한을 1로 둘지 결정한다.

### 3.3 3단계 — 대역별 부담 지도

FFT 결과를 1/3 옥타브 대역으로 분할하고 3~6 kHz 취약성을 반영한다.

**근거**: 달팽이관은 주파수 위치 지도인 토노토피 구조를 가져 특정 주파수의 소음은 해당 위치의 유모세포를 선택적으로 손상시킨다. 그중 3~6 kHz, 특히 4 kHz 부근의 외유모세포가 가장 취약해 소음성 난청의 대표 징후는 청력도상 **4 kHz 노치**로 나타난다. 국내 임상 보도에서도 소음성 난청이 4 kHz 부근에서 시작해 점차 저주파로 진행한다는 설명이 확인된다.

첨도가 커질수록 청력도의 노치가 깊어지고, 노치가 깊어지기 시작하는 주파수가 3 kHz에서 1 kHz로 이동한다는 보고도 있다.

> **중요 설계 결정**: 대역별 가중치는 **총 선량에 곱하지 않고 별도 지도로만 표시한다.** Google Android 14의 계산 음향 선량이 주파수 의존적 분석을 하면서도 그 목적이 단일 선량 값을 더 정확히 계산하기 위한 가중에 머물러, 어느 대역이 부담받는지를 사용자에게 분리해 제시하지 않는 것과 명확히 구분되는 지점이다.
>
> Applied Acoustics의 복합 소음용 적응형 가중 연구는 고레벨 충격성 소음에 A-가중이 부적절할 수 있음을 지적하나, 저주파 소음의 위험도는 학계 증거가 엇갈리므로 본 연구는 이를 과잉 주장하지 않는다.

### 3.4 4단계 — 회복 적분기 F(t)

**핵심 개념: 물을 부으면서 동시에 바닥 구멍으로 새는 그릇.**

```
dF/dt = g × D(t) − F/τ
```

- `D(t)` : 보정된 순간 부담률
- `g` : 축적 계수
- `τ` : 회복 시간상수

빠른 성분과 느린 성분 두 개의 시간상수를 둔다.

```
F(t) = F_fast(t) + F_slow(t)

dF_fast/dt = g₁·D(t) − F_fast/τ_fast     τ_fast ≈ 30분
dF_slow/dt = g₂·D(t) − F_slow/τ_slow     τ_slow ≈ 240분
```

**동작**:
- 듣는 동안: 붓는 속도 > 새는 속도 → 차오름
- 이어폰 제거: 붓는 항이 0 → 새는 항만 작동
- 30분 휴식 → 빠른 성분이 절반 이상 빠져 게이지가 눈에 띄게 하강
- 장시간 휴식 → 느린 성분이 남아 **완전히 0으로 복귀하지 않음**

**근거 문헌**

**Patuzzi (1998)** — 순음 과다자극 전후 TTS의 발생·회복을 측정하여 다중지수 시간경과를 보고. 발생 시간상수 6.5분·800분, **회복 시간상수 30분·240분·800분**. 시간상수는 과다자극 지속시간에 의존하지 않으나 지수 계수는 의존한다. 노출 후 첫 5분의 급속 회복은 내유모세포-일차구심신경 시냅스의 단기 교란에 기인한 것으로 해석된다.

> ⚠ **중대한 한계**: 이 실험은 **인간 피험자 단 1명(논문 저자 본인)**을 대상으로 한다. 성인 남성 1명의 데이터이므로 연령·성별 일반화는 애초에 논의 대상이 아니다. 본 앱은 이 값을 **초기값(prior)으로만** 사용하며, 절대 회복량 예측이 아니라 상대적 회복 추세 제시에 한정한다.

**Stephenson et al. (1978)** — 간헐 노출이 동일 총 에너지의 연속 노출보다 역치변동이 작고 회복도 빠름. 등에너지 가설과 직접 충돌하는 결과. Patuzzi(1998)에서도 간헐 노출이 연속음보다 TTS를 훨씬 적게 유발해 등에너지 모델 예측과 불일치하며 회복 시간경과도 달랐다는 결과가 재확인된다.

**Kujawa & Liberman** — 은닉성 난청. 역치가 회복되어도 청신경 시냅스 손상은 남는다.

**→ 따라서 본 모델은 완전 회복이 아닌 부분 회복을 전제로 설계한다.**

일반 문헌에서 TTS는 자극 스펙트럼·노출 수준·지속시간에 주로 좌우되고, PTS 쪽이 노출기간·피험자 나이·이독성 물질 등 여러 요인과 관련된다고 본다. 회복 동역학의 연령·성별 의존성은 아직 정립된 정량 모델이 없다.

### 3.5 5단계 — 정규화 및 임계값

> ⚠ **필수 설계 결정**: F(t)에는 자연스러운 단위가 없다. g와 τ를 어떻게 잡느냐에 따라 값이 통째로 스케일된다. 따라서 F(t)를 자체 단위로 두지 않고 **주간 허용 선량 대비 비율로 정규화한다.**

```
표시값(%) = F(t) / (주간 허용 선량) × 100
```

**이렇게 해야만**:
1. 80% / 100% 경고선을 H.870에서 그대로 가져올 수 있다
2. 왼쪽 표준 게이지와 오른쪽 유효 게이지가 **같은 축**에서 비교된다
3. "왜 이 숫자에서 경고하는가"에 표준 근거가 생긴다

축이 다르면 두 게이지를 나란히 놓는 것 자체가 무의미해진다.

**기준선량 — WHO-ITU H.870**

| 모드 | 주간 허용 선량 | 등가 조건 | 대상 |
|---|---|---|---|
| Mode 1 | 1.6 Pa²h | 80 dBA × 40시간/주 | 성인 |
| **Mode 2** | **0.51 Pa²h** | **75 dBA × 40시간/주** | **아동·민감 사용자** |

H.870은 사용자가 최초 사용 시 모드를 선택하고 이후 변경할 수 있도록 요구하며, 개인 오디오 시스템이 노출 시간을 추적하고 A-가중·확산음장 보정 선량을 추정할 것, 사전 설정 임계값(예: 80%, 100%)에서 경고할 것, 경고가 확인되지 않으면 볼륨을 자동으로 낮출 것을 요구한다.

> **본 앱은 Mode 2를 기본값으로 채택한다.** 주 사용자가 미성년이므로 1.6 Pa²h를 100%로 두는 것은 표준 취지에 어긋난다. 나이 입력 → 18세 미만 자동 Mode 2. 상수 하나를 바꾸는 작업이지만 표준의 연령 조항을 준수했다는 명확한 신호가 된다.

### 3.6 6단계 — 장기 예측 (ISO 1999:2013)

```
H' = H + N − (H × N)/120
```

**N (소음성 영구역치이동, NIPTS)** — 10~40년 노출:

```
N₅₀ = [ u + v·log(Θ/Θ₀) ] × (L_EX,8h − L₀)²
```

10년 미만:

```
N₅₀(Θ<10) = [ log(Θ+1) / log(11) ] × N₅₀(Θ=10)
```

u, v, L₀는 **주파수별로만** 표에 규정된 상수다.

**H (연령 관련 역치)** — Annex A (Database A):

```
H = a(Y − 18)² + H₁₈
```

계수 a와 H₁₈은 **성별·주파수별로** 표에 규정된다.

**분포**: N의 통계 분포는 두 개의 서로 다른 정규분포의 반쪽으로 근사된다. 중앙값보다 나쁜 상위 절반은 파라미터 du로, 하위 절반은 더 작은 산포 dl로 특징지어진다. Q(5≤Q<50%)와 Q(50%<Q≤95%)에 대해 각각 별도 공식이 적용된다.

## 4. 연령·성별 의존성 분석

각 구성요소가 개인차를 어디까지 반영하는지 정밀 조사한 결과:

| 구성요소 | 연령 | 성별 | 근거 모집단 |
|---|---|---|---|
| ISO 1999 노화항 H | ✅ 연속 함수 | ✅ 남/녀 별도 표 | 성인, 선별집단 |
| **ISO 1999 소음항 N** | ❌ **없음** | ❌ **양성 공통** | 성인 노동자 |
| H.870 기준선량 | △ 2단 스위치 | ❌ | — |
| 첨도 보정 β | ❌ | ❌ | 중국 제조업 노동자 |
| 회복 시간상수 τ | ❌ | ❌ | **피험자 1명** |
| A-가중 (ISO 226) | 18~25세 고정 | ❌ | 젊은 성인 |

### 4.1 ISO 1999의 절반만 개인화된다

ISO 1999는 3~8 kHz에서 나이가 들수록 역치가 오르고 여성이 남성보다 청력 손실이 적다고 명시하며, Annex A 표는 성별로 분리되어 있다. 기준점은 "18세 동성 집단 대비"다.

**그러나 NIPTS 식은 양성 공통으로 주어지며 연령 항이 없다.** u, v, L₀는 주파수에 의해서만 달라진다.

**→ 즉 노출로 인한 손상량 N은 16세든 45세든, 남자든 여자든 동일하게 산출된다. 연령·성별은 그 위에 얹히는 노화 곡선 H를 통해서만 반영된다.**

또한 ISO 1999는 **성인 집단의 통계적 예측용**이며 개인의 확정적 진단용이 아니다. 고등학생 대상 앱이 이 모델을 적용하는 것은 이미 표준의 검증 범위를 벗어난 외삽이다.

### 4.2 첨도 계수는 연령·성별을 '제거한 뒤' 추정된 상수

첨도 연구들이 연령·성별을 무시한 것이 아니다. **정반대로, 그 효과를 먼저 소거한 뒤 계수를 추정했다.**

- 측정 청력역치에서 ISO 1999(2013) Table B.3의 연령·성별별 값을 차감해 NIPTS를 계산
- 회귀분석에서도 나이·성별·노출기간·LAeq를 통제한 상태에서 첨도의 독립 효과를 확인 (오즈비 1.18, p<0.05)
- 복합 소음이 3·4·6·8 kHz에서 가우시안 소음보다 높은 NIHL 위험을 유발하는 것도 연령·성별·CNE 보정 후 확인됨

**→ 첨도 계수는 "평균적인 성인에게서 연령·성별 효과를 소거하고 남은 순수 물리 효과"다. 개인화를 안 한 것이 아니라 개인화가 불가능하도록 설계된 값이다.**

### 4.4 계획서에 명시할 한계 문단 (초안)

> 본 모델의 보정 계수는 모두 중국 성인 제조업 노동자 및 소수 피험자 실험에서 유도된 값이며, 특히 회복 시간상수는 단일 피험자 데이터에 근거한다. 청소년 이어폰 사용자 집단에서 검증된 바 없다. 따라서 본 앱의 유효 청각 피로도는 절대적 손상량이 아니라 **사용자 자신의 습관 간 상대 비교 지표**로 해석되어야 한다.

### 4.5 하지 말아야 할 것

**첨도 계수나 회복 시간상수에 임의의 연령 계수를 곱하지 않는다.** 근거가 없다. 없는 개인화를 만들어내는 순간 문헌 해석의 신뢰도가 무너진다.

## 5. AI 레이어 설계

### 5.1 배치 원칙

```
① ② ③ ④ ⑤ ⑥ ⑦  ← 결정론적, 표준·논문으로 검증 가능
              ⑧  ← AI, 표준이 답하지 못하는 영역
```

### 5.2 AI-1. 궤적 예측 및 사전 경고

**해결하는 문제**: 계획서 2.1의 네 번째 결함 "미래를 예측하지 않는다". 현행 ⑤번 모듈은 N년 후만 본다. **오늘 저녁, 이번 주말이라는 행동 가능한 미래가 비어 있다.**

| 기존 | AI 적용 후 |
|---|---|
| "80%에 도달했습니다" (사후) | "지금 속도면 토요일 23시경 한도를 넘습니다" (사전) |

**입력**: 요일 × 시간대 부담 이력, 최근 세션 패턴
**출력**: 향후 24~72시간 선량 궤적, 한도 도달 예상 시점

**모델 선택 및 실험 설계**

데이터가 수 주치에 불과하므로 반드시 베이스라인 비교를 수행한다.

| 후보 | 성격 |
|---|---|
| 지수평활 (Holt-Winters) | 베이스라인 |
| 선형회귀 (요일·시간대 더미) | 베이스라인 |
| 소형 GRU / LSTM | 학습 모델 |

평가: MAE, 한도 도달 시점 예측 오차, 시계열 교차검증

> **중요**: 소형 GRU가 베이스라인을 이기지 못할 가능성이 상당하다. **그 결과를 그대로 보고서에 기재한다.** "데이터 규모상 단순 모델이 우수해 이를 최종 채택했다"는 서술은 감점 요인이 아니라 실험 설계 능력의 증거다.

### 5.3 AI-2. 볼륨 크리프 탐지 ★ 핵심

**해결하는 문제**: 사용자가 점진적으로 볼륨을 올리는 것은 소음성 난청의 행동적 징조다. 그러나 현행 시스템은 이를 전혀 보지 않는다.

**결정적 장점 — 교정 문제를 완전히 우회한다.**

절대 SPL을 몰라도 된다. 동일 기기에서 동일 사용자의 볼륨이 **올라가고 있다는 사실 자체**가 신호이기 때문이다. 원칙 3과 완벽히 일치한다.

**두 개의 시간 스케일**

| 스케일 | 해석 |
|---|---|
| 세션 내 상승 | 일시적 역치변동(TTS)의 행동적 흔적 — "지금 귀가 둔해져 볼륨을 올리고 있다" |
| 주 단위 상승 | 누적 변화 가능성 — 더 주의 필요 |

**왜 AI가 필요한가 — 교란 요인 통제**

볼륨 상승에는 무해한 원인이 훨씬 많다. 단일 임계값으로는 불가능하다.

| 교란 요인 | 통제 방법 |
|---|---|
| 주변 소음 (지하철·버스) | 마이크로 환경 소음 레벨 동시 측정 |
| 콘텐츠 변화 (팟캐스트 → EDM) | 콘텐츠 분류 (AI-3) |
| 이어폰 교체 | 기기 ID 변경 감지 |
| 재생 기기 변경 (폰 ↔ 노트북) | **(재생 기기 × 출력 장치) 조합별로 따로 모델링** — 기기마다 볼륨 숫자의 의미가 다르므로 섞지 않는다 (14.4절) |
| **청각 피로 / 청력 변화** | **위 요인들을 통제하고 남은 잔차** |

**모델 구조**

```
볼륨 = f(주변소음, 콘텐츠유형, 기기, 시간대) + 잔차
                                                 ↓
                                      잔차 시계열의 추세 탐지
                                      (변화점 탐지 / CUSUM)
```

**→ "교란 요인을 제거하고 남은 잔차의 추세를 탐지"하는 문제. 이 프로젝트에서 AI를 쓴 이유를 가장 명확히 설명할 수 있는 지점이다.**

### 5.4 AI-3. 콘텐츠 분류

**해결하는 문제**: 현재 첨도 β는 통계량 하나다. β=8이 게임 총소리인지 EDM 킥드럼인지 팟캐스트 파열음인지 구분하지 못한다.

**방법**: 멜스펙트로그램 → 사전학습 오디오 분류 모델. TensorFlow.js에서 **YAMNet**(AudioSet 521클래스 사전학습)을 브라우저에서 직접 실행 가능. 자체 학습 불필요.

**얻는 것**: **행동 귀속(attribution)**
> "이번 주 부담의 62%가 게임에서 발생했습니다"

사용자가 실제로 바꿀 수 있는 정보는 dB 숫자가 아니라 이것이다.

> ⚠ **제약**: 분류 결과를 선량 계산에 곱하지 않는다. 라벨링·집계 및 AI-2의 교란 통제 변수로만 사용한다. (원칙 1)

### 5.5 AI-4. 리포트 및 코칭 (보조)

수치 상태를 자연어 조언으로 변환. 구현은 간단하나 단독으로는 약하므로 보조 기능으로 배치한다.

**제약**:
- 원시 오디오·이력 전송 금지, **요약 수치 몇 개만** 전송 (로컬 저장 원칙 위배 방지). 14절의 계정 동기화와는 별개로, 외부 언어모델 API에는 주간 요약 수치 몇 개만 보낸다
- 진단 표현 금지 (원칙 2)

**병원 연계**: 진단은 하지 않되 "가까운 이비인후과 찾기" 출구는 제공한다.

> ❌ "당신은 난청이니 병원에 가세요"
> ⭕ "정확한 확인은 이비인후과에서 가능합니다"

예방 앱이 의료로 연결되는 경로를 만든다는 점에서 기대효과 항목이 강화된다.

### 5.6 보류 항목 — 앱 내 자가 청력 측정

**아이디어**: 설치 시 청력 테스트로 개인별 역치를 측정하고, 1~2주마다 재점검

**막힌 벽**:
1. 교정되지 않은 이어폰으로는 dB HL을 알 수 없다. 동일 디지털 진폭이라도 기기·이어폰 감도(EN 50332)·삽입 깊이에 따라 20~30 dB 차이가 나며, dB는 로그 스케일이라 이 오차가 선량에서 수백 배로 증폭된다.
2. **논리적 모순**: 계획서 3.1.1에서 Apple의 청력검사 기능이 만 18세 이상 제한이라는 점을 한계로 지적했다. Apple조차 성인에게만 여는 기능을 미성년 대상 앱이 첫 화면에서 수행하면 심사에서 반드시 지적된다.

**축소 형태로 살리기**

| 금지 | 허용 |
|---|---|
| 절대 역치 표시 | 첫 주 대비 상대 변화만 |
| "청력검사" | "귀 컨디션 체크" |
| 숫자 결과 | 추세선만 |
| 조건 무관 측정 | 기기·볼륨 고정, 조건 이탈 시 측정 무효 처리 |

**대안**: 개인 회복 시간상수 τ를 베이지안 파라미터 추정으로 개인화 (딥러닝이 아닌 적응형 추정). 일정이 빠듯하면 **"향후 과제"로 제시**하는 것도 충분히 타당한 선택.

## 6. UI 설계

> **개정 이력**: 초안의 「이중 게이지 + 4화면」 구성을 v2에서 전면 개편했다. 계산 경로(①~⑤)와 AI 레이어(⑧)는 변경되지 않았으며, 같은 값을 어떻게 보여주는가만 달라졌다.

### 6.0 왜 개편했는가

원칙 1~3은 계산에 관한 규율이고, UI에는 별도의 문제가 있다.

주 사용자는 10대인데 첫 화면이 1/3 옥타브 밴드와 첨도 수치로 시작하면 앱을 열지 않는다. 열지 않는 예방 앱은 예방하지 못한다. 반대로 근거를 숨기면 0절에서 선언한 이 프로젝트의 최대 강점 — 화면의 숫자를 표준·논문으로 역추적할 수 있다는 점 — 이 화면에서 사라진다.

**→ 두 요구를 한 화면에서 타협하지 않고, 화면을 두 층으로 나눈다.**

| 층 | 내용 | 진입 |
|---|---|---|
| 1층 (일상) | 캐릭터 상태, 정규화된 % 하나, 지금 할 행동 한 줄 | 기본 화면 |
| 2층 (근거) | 계산식, 표준·논문 출처, 각 근거의 한계 | 상단 「자세히」 토글 · 숫자 옆 「?」 버튼 |

이는 기능을 줄이는 것이 아니라 접어두는 것이다. 심사·시연에서는 펼쳐서 보여주면 된다.

### 6.1 코코 — 캐릭터가 곧 계기판

달팽이관(cochlea)은 어원 그대로 달팽이 껍데기 구조이며, 껍데기 나선의 위치가 곧 담당 주파수다(토노토피). 이 사실을 그대로 UI로 옮긴다.

**마스코트 '코코'의 껍데기 나선 = 1/3 옥타브 19밴드 대역별 부담 지도**

- 바깥쪽 감김 = 기저부 = 고주파(8 kHz) / 안쪽 = 첨부 = 저주파(125 Hz)
- 나선 위 각 구간의 색과 굵기 = 해당 대역의 누적 부담
- 3.3절의 4 kHz 지점을 껍데기 위에 표식으로 고정 표시
- 눈자루 처짐 정도 = 현재 F(t) 수준

**설계상의 이득**: 7.2절에서 지적한 차별점 — "Google은 주파수 분석 결과를 다시 하나의 선량 값으로 접지만 우리는 접지 않는다" — 이 그림 한 장으로 설명된다. 막대그래프로는 성립하지 않는 설명이다.

> ⚠ **중대한 설계 제약 — 코코는 유모세포가 아니다**
>
> 초기 아이디어 단계에서 "유모세포 캐릭터가 지쳐서 누워 있다가 휴식 후 기운을 차린다"는 안이 검토되었으나 기각했다. 유모세포는 피로해서 눕는 것이 아니라 손상되면 재생되지 않는다(1.1절). 캐릭터가 세포 상태를 흉내 내면 사용자에게 **잘못된 안심**을 주며, 이는 원칙 2의 직접 위반이다.
>
> 따라서 코코는 **피로 지표 F(t)를 눈에 보이게 만든 캐릭터**로만 정의하고, 앱 안의 근거 시트에서 이를 명시한다. 코코가 기운을 차리는 것은 F(t)가 내려갔다는 뜻이지 귀가 회복됐다는 뜻이 아니다.

**껍데기 색은 초기 상태로 복귀하지 않는다.** 대역 부담값에 하한(느린 성분 잔여분)을 두어, 아무리 쉬어도 첫 주의 색으로는 돌아가지 않게 한다. 3.4절의 "완전 회복이 아닌 부분 회복" 전제를 시각적으로 강제한 것이며, 쉬면 풀 회복되는 통상의 육성 게임과 구분되는 지점이다.

### 6.2 이중 게이지 — 프로젝트의 핵심 비교 (유지)

초안의 좌우 분리 게이지를 **단일 축 위의 막대 + 기존 방식 마커**로 바꾸었다. 3.5절이 요구한 "같은 축" 조건을 형태로도 강제하기 위해서다.

| | 값 예시 | 계산 방식 |
|---|---|---|
| 막대 (SafeEar) | 55% | 첨도 보정 + 회복 반영 |
| 마커 (기존 방식) | 39% | 총에너지 × 시간, 휴식 미반영 |

**두 값의 차이가 곧 본 연구의 기여다.** 차이의 방향은 상황에 따라 바뀐다.

- 뾰족한 소리를 몰아서 청취 → SafeEar 값이 더 높음
- 잔잔한 음악을 휴식과 함께 청취 → SafeEar 값이 더 낮음

80% / 100% 눈금은 H.870에서 그대로 가져온다(3.5절).

### 6.3 「10년 뒤 이 노래」 — 신규 기능

**해결하는 문제**: 3.6절의 ISO 1999 장기 예측은 지금까지 청력도 그래프로만 제시되었다. 그러나 dB 단위 역치이동 그래프는 10대에게 아무것도 체감시키지 못한다.

**방법**: 주파수별 예측 NIPTS 곡선을 **부호 반전해 EQ 필터로 걸어**, 지금 재생 중인 소리에 그대로 적용한다.

```
ISO 1999 예측 역치이동 N(f)  →  EQ 게인 −N(f)  →  실시간 필터 적용
```

- 구현: Web Audio API BiquadFilter — peaking(4 kHz, Q≈1.15) + highshelf(6.3 kHz)
- 재생 중 필터 계수만 교체하므로 즉시 A/B 비교가 가능하다

**3단 비교**

| 버튼 | 내용 |
|---|---|
| 지금 | 필터 없음 (기준) |
| 10년 뒤 | 현재 습관이 그대로 이어질 경우 |
| **10년 뒤 (볼륨 10% 감소)** | **줄였을 때의 같은 10년** |

> **세 번째가 핵심이다.** 겁주기로 끝나는 예방 앱은 사용자가 지운다. 6.4절 주간 리포트에서 노화분과 소음분을 색으로 분리하는 것과 같은 메시지 — "이 중 바꿀 수 있는 것은 소음분뿐" — 을 소리로 옮긴 것이다.

부수적으로, 이 기능은 **10초 안에 체감시킬 수 있는 유일한 기능**이므로 예선 영상과 본선 시연에서 설명 비용이 가장 낮다.

> ⚠ **한계 명시**: 이것은 청력검사가 아니다. 사용자의 실제 역치를 측정한 것이 아니라 **예측값을 소리로 옮긴 시나리오**이며, 화면에 그렇게 표기하고 오차범위를 병기한다. 4.2절의 외삽 한계(성인 집단 통계식을 청소년에게 적용)가 이 기능에도 그대로 적용된다.

- 코코 + 나선 게이지, 정규화된 % 하나
- 이중 게이지(막대 + 기존 방식 마커)
- "지금 30분 쉬면 47%까지 내려갑니다" — 지금 할 행동 한 줄
- 한도 도달 예상 시점 (AI-1)
- 조용한 날 스트릭 (로컬 전용, 6.7절)
- 현재 음량 · 첨도 β · 오늘 누적 (요약 3칸)

**② 귀 지도**
- 코코의 껍데기 원형 + 일자로 편 19밴드 막대 (같은 데이터, 두 표현)
- 3~6 kHz 취약 대역 강조, 4 kHz 노치 설명
- 이 대역을 올린 콘텐츠 (AI-3)

**③ 회복 코치**
- 코코 3단계 비교: 지금 → 30분 뒤 → 자고 나서 (껍데기 색이 옅어지다 멈춤)
- 빠른 피로 / 느린 피로 분리 곡선 + 기존 계산 방식 점선
- 휴식 타이머, 휴식 시간별 예상 회복량

**④ 10년 뒤** (6.3절)
- 3단 EQ 비교 + 재생
- 예상 EQ 곡선 (세 시나리오 중첩 표시)
- 무엇이 먼저 사라지는가 (심벌즈 · 자음 · 베이스)
- 36세 시점 추정 청력도 (노화분/소음분 색상 분리, 오차범위 병기)

**⑤ 주간 리포트**
- 요일 × 시간대 히트맵
- 콘텐츠별 부담 귀속 (AI-3)
- 볼륨 추세 (AI-2)
- 이비인후과 연계 출구

### 6.5 근거 시트 — 강점을 문서가 아니라 기능으로

화면의 숫자 옆 「?」를 누르면 그 값의 출처가 뜬다.

- 표준 / 논문 태그 구분
- **해당 근거의 한계를 같은 화면에 함께 표시** — 회복 시간상수를 띄우면 Patuzzi(1998)와 함께 "피험자 1명(논문 저자 본인)"이 나온다
- 상단 「자세히」를 켜면 각 카드에 계산식이 펼쳐진다

0절이 선언한 역추적 가능성을 **조작 가능한 기능**으로 구현한 것이다. 심사위원이 직접 눌러 확인할 수 있다는 점에서, 같은 내용을 보고서에만 적어두는 것과 설득력이 다르다.

### 6.6 1.2절의 네 가지 정보 손실과 화면의 대응

| 기존 시스템이 버리는 것 | 어느 화면이 복원하는가 |
|---|---|
| ① 소리의 시간 구조 (첨도) | ① 오늘 — 첨도 β 노출, 이중 게이지의 차이 |
| ② 휴식 (회복 동역학) | ③ 회복 — 코코 3단계, 2-τ 분리 곡선 |
| ③ 주파수 분포 (토노토피) | ② 귀 지도 — 코코 껍데기, 19밴드 분리 표출 |
| ④ 미래 | ① 사전 경고(AI-1), ④ 10년 뒤(ISO 1999) |

### 6.7 채택하지 않은 것 — 또래 비교 · 학급 랭킹

게이미피케이션 검토 과정에서 "우리 반 귀 건강 평균 점수" 같은 또래 경쟁 기능이 후보에 올랐으나 **기각했다.**

1. **개인 데이터 원칙 위배** — 2.2절 ⑥에서 로컬 우선 보관을 명시하고 설정 화면에서 사용자에게 약속한다. v3에서 계정 동기화(14절)가 추가되었지만, 동기화된 기록은 **본인 계정 안에서 본인 기기끼리 합치는 데만** 쓰고 다른 사람과 비교하는 데는 쓰지 않는다. 랭킹은 이 약속과 양립하지 않는다.
2. **낙인 위험** — 1.3절대로 국내 청소년의 16~17%가 이미 역치 이탈 또는 소음성난청 상태다. 점수 줄 세우기는 그 집단에게 예방이 아니라 낙인으로 작동한다.

**대신 개인 스트릭만 로컬로 유지한다.** 비교 대상은 반 친구가 아니라 지난주의 자신이며, 이는 원칙 3(절대 판정보다 상대 비교)과도 일치한다.

> 설정 화면에 "친구와 비교하기 — 만들지 않았습니다"와 그 사유를 명시한다. 기능이 없는 것과 **판단해서 넣지 않은 것**은 다르게 읽힌다.

## 7. 선행 시스템과의 비교

### 7.1 Apple

2020년 iOS 14에서 건강앱 내 "헤드폰 오디오 수준" 도입. 기반 표준은 EN 50332-3과 ITU-T H.870으로, A-가중과 확산음장 보정을 거친 음압 제곱을 시간 적분한 Pa²h를 사용한다. 최근 7일 롤링 윈도우에서 80 dB 이상 노출이 누적 40시간에 도달하면 100%로 간주해 알림을 보내고, 확인하지 않으면 볼륨을 자동으로 낮춘다. 집계 해상도는 80 dBA 미만이 30초 등가 연속 레벨, 그 이상은 5초 등가 연속 레벨로 위험 구간에서만 시간 해상도를 높이는 설계다.

**한계**: 7일 한계는 미디어 오디오에만 적용되고 통화는 집계되지 않는다. 청력검사·보청 기능은 만 18세 이상 대상이다. 세 기능 모두 이미 발생한 손실을 측정하거나 보완·억제할 뿐, 현재 습관이 축적하는 부담을 구조적으로 분석하지 않는다.

**활용**: HealthKit의 `headphoneAudioExposure` 식별자로 서드파티 접근이 가능하다는 점은, 본 연구가 **실사용 노출 데이터를 검증 기준선으로 삼을 수 있는 근거**가 된다.

### 7.2 Samsung, Google

- **Samsung**: One UI Volume Monitor로 일간·주간 볼륨 패턴 분석, WHO 권고 대비 상태 안내. Samsung Health의 소음 기능은 워치 마이크의 주변 소음과 스마트폰 출력을 함께 모니터링하는 방향으로 확장 중이나 산출 방식은 여전히 등에너지 선량.
- **Google**: Android 14부터 계산 음향 선량 도입. 고정 볼륨 인덱스가 아니라 재생 오디오의 주파수 의존적 분석으로 유해도를 추정한다는 점에서 세 플랫폼 중 신호처리상 가장 진전된 구현. **다만 주파수 분석의 목적이 단일 선량 값을 더 정확히 계산하기 위한 가중에 머물러, 어느 대역이 부담받는지를 사용자에게 분리해 제시하지 않는다.**

**→ 본 연구와 가장 가까우면서도, 주파수 정보를 다시 하나의 숫자로 접어 넣는다는 점에서 명확히 구분된다.**

## 8. 검증 계획

| 단계 | 방법 | 판정 기준 |
|---|---|---|
| V1. 선량 재현 | A-가중 음압 제곱의 시간 적분으로 H.870 계산 선량 재현 | 표준 계산값과 일치 |

| V8. 이식 일치 (신규) | 같은 골든 WAV를 웹(TS)·안드로이드(Kotlin) 등 모든 구현에 입력 (16.2절) | 모든 구현의 출력이 허용오차 안에서 일치 |

V1→V2가 **본 프로젝트의 검증 앵커**다. 에너지 선량 계산은 국제표준으로 확립되고 상용 앱에도 완전히 반영되어 있으므로, 본 연구는 이를 재현하는 데 그치고 그 위에서 차별화를 시도한다.

## 12. 예상 질문 대비

**Q. AI 대회인데 핵심 계산에 AI가 없네요?**

> 측정에는 AI를 쓰지 않았습니다. 국제표준과 논문으로 검증 가능해야 하기 때문입니다. AI는 그 표준이 답하지 못하는 것 — 이 사용자가 앞으로 어떻게 될 것인가 — 에만 사용했습니다.

측정/해석 분리가 명확하면 AI가 적게 쓰인 것이 약점이 아니라 **설계 판단**으로 읽힌다.

**Q. 피로도 50%는 무슨 근거인가요?**
> 자체 단위가 아니라 H.870 주간 허용 선량 대비 비율입니다. 경고 시점 80%·100%도 표준에서 가져왔습니다.

**Q. 성인 노동자 데이터를 청소년에게 적용해도 되나요?**
> 되지 않습니다. 그래서 절대 손상량이 아니라 사용자 본인의 습관 간 상대 비교 지표로 제시하며, 이를 한계로 명시했습니다. (4.4절)

**Q. 회복 시간상수의 근거는?**
> Patuzzi(1998)의 30·240·800분입니다. 다만 단일 피험자 실험이므로 초기값으로만 사용하고, 개인화는 향후 과제로 두었습니다.

**Q. 캐릭터를 넣으면 과학적 엄밀성이 떨어지지 않나요?**
> 코코의 껍데기가 곧 대역별 부담 지도입니다. 장식이 아니라 계기판이고, 나선 위 위치가 실제 달팽이관 토노토피 배열과 일치합니다. 다만 코코를 유모세포로 설정하는 안은 기각했습니다. 유모세포는 피로해서 눕는 것이 아니라 손상되면 재생되지 않기 때문입니다. (6.1절)

**Q. 10년 뒤 소리는 실제로 그렇게 들린다는 뜻인가요?**
> 아닙니다. 사용자의 청력을 측정한 것이 아니라 ISO 1999 예측값을 EQ로 옮긴 시나리오입니다. 화면에 그렇게 표기하고 오차범위를 함께 보여줍니다. (6.3절)

**Q. 친구들과 경쟁하게 하면 더 많이 쓰지 않을까요?**
> 국내 청소년의 16~17%가 이미 소음성난청이거나 역치 이탈 상태입니다. 점수를 줄 세우면 그 집단에게는 예방이 아니라 낙인이 됩니다. 로컬 저장 원칙과도 충돌해서 넣지 않았고, 설정 화면에 그 사유를 명시했습니다. (6.7절)

**Q. 볼륨이 오르는 건 지하철 탔기 때문일 수도 있잖아요?**
> 그래서 주변 소음·콘텐츠 유형·기기 변경을 통제 변수로 두고, 잔차의 추세만 탐지합니다. 단일 임계값으로는 불가능하기 때문에 AI를 사용한 지점입니다.

**Q. 넷플릭스처럼 소리를 막아 둔 앱은 어떻게 하나요?** (v3)
> 막힌 앱은 소리 파형을 받을 수 없으므로 볼륨과 재생 시간만으로 에너지 선량을 계산합니다. 기존 세 플랫폼과 같은 방식입니다. 첨도와 대역 지도는 "측정 불가"로 표시하고 추정치로 채우지 않습니다. 화면에 세션마다 측정 등급을 붙여 어떤 숫자가 실제 파형에서 나왔는지 구분합니다. (13.3절)

**Q. 아이폰에서는 되나요?** (v3)
> iOS 27 이상에서는 애플이 새로 연 화면·소리 캡처 기능으로, 사용자가 측정을 시작한 동안 다른 앱의 소리를 실제로 분석합니다. 그 밖의 시간과 iOS 26 이하에서는 Apple이 기록하는 헤드폰 노출 레벨을 HealthKit으로 읽어 선량·회복·장기 예측을 계산하고, 첨도와 대역은 청취 기록 기반 추정으로 보완하되 실측과 구분해 표시합니다. (13.4절, 17절)

**Q. 폰이랑 노트북에서 따로 들으면요?** (v3)
> 귀는 하나이므로 계정으로 묶어 합산합니다. 합산은 에너지(Pa²h) 단위로 하고, 회복 적분기는 합친 타임라인 위에서 다시 계산합니다. 다만 볼륨 추세는 기기마다 볼륨 숫자의 의미가 달라 기기별로 따로 봅니다. (14절)

**Q. 제 소리가 서버에 올라가나요?** (v3)
> 올라가지 않습니다. 원시 오디오는 기기 안에서 1초 단위 특징값으로 바뀐 직후 버려지고, 서버에는 1분 요약 숫자만 올라갑니다. 동기화는 선택이며 끄면 기기 안에만 저장됩니다. (14.2절)

### 13.0 무엇이 필요한가 — "크기"와 "모양"

이 앱이 소리에서 얻어야 하는 정보는 두 종류다.

| 정보 | 쓰이는 곳 | 필요한 입력 |
|---|---|---|
| **크기** (얼마나 크게 들었나) | 에너지 선량, F(t), ISO 1999 | 디지털 레벨 + 볼륨 + 기기 프로필 — **레벨값만 있어도 가능** |
| **모양** (어떤 소리였나) | 첨도 β, 1/3옥타브 대역 지도, 콘텐츠 분류 | **소리 파형(PCM) 자체**가 필요 |

### 13.2 질문별 정리

**"넷플릭스를 비롯한 대부분의 앱은 출력 소리에 접근하지 못하게 한다"는 말은 맞는가?**
- **안드로이드: 반만 맞다.** 최신 앱(targetSdk 29 이상)은 미디어·게임 소리를 기본적으로 **캡처 허용** 상태이고, 앱이 직접 끄면 막힌다. 넷플릭스 같은 DRM 스트리밍 앱은 끄는 경우가 많다. 유튜브·스포티파이·멜론·틱톡·게임 등은 앱마다 다르므로 **직접 시험해서 "캡처 가능 앱 표"를 만든다** (15절 Phase 0). 이 표는 보고서에도 그대로 들어갈 수 있는 1차 자료다.
- **iOS·iPadOS: 버전에 따라 다르다 (v3.2 수정).** iOS 26 이하는 ReplayKit 방송으로 우회하는 방법뿐이고 불안정하다. **iOS 27부터는 공식 API(ScreenCaptureKit)로 다른 앱의 소리를 받을 수 있다.** 애플 개발자 포럼에는 iOS 27에서 **애플 뮤직 앱 소리가 실제 PCM(48 kHz 스테레오)으로 캡처되었다는 보고**가 있다. 반면 Zoom·Teams 같은 통화 앱 소리는 전부 0으로 들어왔다고 한다. 스포티파이·유튜브·넷플릭스·게임은 아직 확인된 보고가 없다 (17.8절).
- **윈도우·맥: 대부분 받을 수 있다.** 다만 보호 콘텐츠 재생 경로는 예외일 수 있어 확인이 필요하다.

**막힌 앱을 재생할 때는?**
등급 C로 내려간다. 안드로이드에서도 볼륨값, 출력 장치 종류, "무언가 재생 중인지"는 알 수 있다. 알림 접근 권한을 받으면 미디어 세션에서 **어느 앱이 재생 중인지**도 알 수 있어, 파형 없이도 콘텐츠 귀속(AI-3의 일부)은 가능하다. 에너지 선량은 계속 계산되므로 최소한 기존 3사 수준은 유지된다.

### 13.3 크기와 모양을 따로 얻는다 — 설계상 이득

**첨도 β와 대역 분포 비율은 신호 크기에 무관하다.** 신호 전체에 상수를 곱해도 β = E[(x−μ)⁴]/σ⁴는 그대로이고, 대역 간 비율도 그대로다. 따라서:

```
모양 (β, 대역 비율)  ← 캡처한 파형      (볼륨 적용 전 신호여도 무방)
크기 (dB SPL 추정)  ← 디지털 레벨(dBFS) + 볼륨 곡선 + 기기·이어폰 프로필
```

캡처한 신호가 시스템 볼륨 적용 **전**인지 **후**인지는 플랫폼마다 다를 수 있다(9절 #11, 실험으로 확인). 위처럼 나누면 어느 쪽이든 설계가 무너지지 않는다. 볼륨 적용 전 신호라면 볼륨값을 따로 읽어 곱하고, 적용 후 신호라면 곱하지 않으면 된다.

**한계 — 캡처 지점 뒤에서 일어나는 일은 보이지 않는다**
- 제조사 음향 효과(삼성 Dolby Atmos·이퀄라이저 등)가 캡처 지점 뒤에서 적용되면 실제 귀에 들어가는 스펙트럼과 다르다
- 이어폰 자체 EQ, 노이즈 캔슬링, 공간 음향, 이어폰 쪽 볼륨, 블루투스 절대 볼륨
- 이어폰 착용 상태(삽입 깊이, 밀착도)

→ 근거 시트(6.5절)의 측정 등급 카드에 이 한계를 함께 띄운다.

**출력 장치 판별이 필요하다**
H.870은 개인 음향기기(이어폰·헤드폰) 기준이다. 스피커로 재생한 소리는 선량에 넣으면 안 된다. 다기기 합산(14절)에서는 특히 중요하다.
- 안드로이드: 현재 출력 장치 종류(유선 헤드폰, 블루투스, USB 헤드셋, 스피커)를 읽을 수 있다
- 윈도우: 출력 장치의 형태 정보(헤드폰/스피커)를 읽을 수 있으나 블루투스는 부정확할 수 있다
- 맥: 출력 장치 종류 확인 가능
- 웹: 알 수 없다 → 사용자가 "이어폰 사용 중"을 직접 확인

### 13.4 iOS·iPadOS 전략 — 포기하지 않고 등급제로

**왜 포기할 수 없는가**: 한국 10~20대는 아이폰 비율이 높은 편이다(한국갤럽 2023년 조사에서 18~29세 아이폰 사용 약 65% — 최신 수치 확인 권장). iOS를 빼면 주 사용자층의 상당수가 빠진다.

| 기능 | iOS에서 | 등급 |
|---|---|---|
| 에너지 선량, F(t), ISO 1999, AI-1 | HealthKit 헤드폰 노출 레벨로 계산 | C |
| 볼륨 크리프(AI-2) | 레벨 시계열로 제한적으로 가능 | C |
| 첨도, 대역 지도, 10년 뒤 EQ | **앱 안에서 재생하는 소리**에 한해 | A |
| 다른 앱 소리 정밀 분석 | **iOS 27+: ScreenCaptureKit으로 청취 세션 단위 실측** (17.8절) / iOS 26 이하: ReplayKit 방송으로 짧은 세션만 | B |
| 들은 곡·앱의 모양 추정 | 청취 기록 + 곡 미리듣기 / 콘텐츠 유형 대표 모양 | D |

> **자세한 방안과 조합 방법은 17절**에 정리했다.

**HealthKit은 검증 기준선 역할도 한다** (8절 V2). Apple이 계산한 선량과 우리 계산을 비교할 수 있다.

**테스트 장벽**
- **Mac + Xcode가 반드시 필요하다.** 윈도우 PC로는 iOS 앱을 빌드·디버깅할 수 없다(클라우드 빌드는 가능하지만 디버깅이 어렵다). 팀·학교에 Mac이 있는지 가장 먼저 확인한다.
- 무료 Apple ID로도 본인 기기에 설치해 시험할 수 있다(설치본은 7일마다 다시 설치). 다만 일부 기능(앱 그룹, 확장 간 데이터 공유, TestFlight 배포)은 유료 개발자 계정(연 99달러)이 필요할 수 있다. 교육기관은 수수료 면제 신청 대상이 될 수 있으므로 지도교사와 확인한다.
- HealthKit 실제 데이터는 실기기에서만 시험할 수 있다(시뮬레이터 불가).
- iPadOS는 17부터 건강 앱을 지원하므로 같은 전략을 쓴다.

### 13.5 안드로이드 실무 주의사항

- **Android 10 이상**에서만 동작한다.
- **동의 창 문구가 "화면 녹화/전송"이다.** 10대 사용자가 놀라거나 거부할 수 있으므로 온보딩에서 "화면은 기록하지 않고, 소리도 저장하지 않습니다"를 먼저 설명한다. Android 14부터는 동의를 재사용할 수 없어 세션마다 다시 묻는다.
- 포그라운드 서비스와 상시 알림이 필요하고, Play 스토어에 그 용도를 신고해야 한다.
- **삼성 등 제조사의 배터리 최적화가 서비스를 종료시킬 수 있다.** 최적화 예외를 요청해도 끊길 수 있으므로, 끊긴 구간은 "미측정"으로 기록하고 사용자에게 재시작을 안내한다.
- **화면이 꺼진 상태에서 유지되는지가 가장 중요한 실험 항목이다.** 음악은 대부분 화면을 끈 채 듣는다.
- 구형 Visualizer API(전체 출력 시각화용)는 기기마다 동작이 다르고 8비트 저해상도라 대체 수단으로만 쓴다.
- 테스트: 윈도우나 맥 PC + 안드로이드 폰 USB 연결로 무료. Play 스토어 등록비는 1회 25달러.

### 13.6 컴퓨터(윈도우·맥)에서는?

**된다. 모바일보다 쉽고, 그중 윈도우가 가장 쉽다.** 단 **웹사이트로는 안 되고 설치형 앱**이어야 한다(웹은 매번 공유 창을 눌러야 함).
- 웹 기술로 데스크톱 앱을 만드는 Electron을 쓰면 윈도우에서 시스템 오디오를 비교적 쉽게 받을 수 있어 웹 코드 재사용이 쉽다. 맥 지원 범위는 버전별로 확인이 필요하다.
- 한계: 청소년의 이어폰 노출은 대부분 휴대폰에서 일어난다. **PC 단독으로는 실생활 노출을 대표하지 못한다.** 대신 PC는 개발 중 검증(V1, V10)과 시연에 가장 편한 환경이다.

### 13.7 "웹사이트를 백그라운드로 켜 두고 다른 앱 소리를 분석"은 가능한가?

- **모바일: 불가능하다.** 모바일 브라우저에는 다른 앱 소리에 접근할 경로가 없고, 백그라운드 탭은 OS가 멈춘다.
- **데스크톱: 사이트가 알아서 시작하는 것은 불가능하다.** 사용자가 매번 공유 창에서 화면·탭을 골라야 하고, 그 뒤로는 공유가 유지되는 동안 동작한다. 이는 브라우저가 의도적으로 막아 둔 것이라 우회하면 안 된다.

**→ 웹의 역할을 세 가지로 한정한다.** (1) 자체 재생 분석(등급 A)과 「10년 뒤 이 노래」, (2) 로그인 · 다기기 합산 대시보드, (3) 데스크톱 브라우저 공유 세션 실험. 실생활 캡처는 15절 Phase 2의 수집기 앱이 맡는다.

### 13.8 그 밖에 고려할 것

| 항목 | 내용 | 대응 |
|---|---|---|
| 프라이버시 | 시스템 오디오에는 영상통화 상대 목소리, 온라인 수업, 개인 영상이 섞인다 | 캡처 모듈이 **특징값만 내보내도록 코드 구조로 강제**. 녹음·저장 기능은 만들지 않는다 |

## 14. 계정 기반 다기기 누적 (v3 신규)

### 14.1 왜 필요한가

**귀는 하나다.** 폰에서 2시간, 노트북에서 1시간, 패드에서 30분을 들었다면 귀에는 3시간 30분이 쌓인다. 기기마다 따로 계산하면 각각은 "괜찮음"으로 보여도 합치면 한도를 넘을 수 있다.

기존 플랫폼은 대체로 자기 생태계 기기끼리만 보고, **OS를 가로질러 한 사람 기준으로 합산하는 서비스는 확인되지 않는다** (7.3절 비교표 추가 행). 이는 SafeEar의 추가 차별점이 된다.

### 14.2 무엇을 올리고 무엇을 올리지 않는가

| 데이터 | 기기 안 | 서버 |
|---|---|---|
| 원시 오디오 | 처리 직후 폐기 | ❌ **절대 올리지 않음** |
| 1초 프레임 값 | 로컬 보관 (기간 제한) | ❌ |
| **1분 요약 레코드** | ✅ | ✅ (동기화를 켠 경우만) |
| 콘텐츠 라벨 | ✅ | 범주만 (음악/게임/영상 등). 앱 이름은 선택 |
| 나이 구간, 성별 | ✅ | 선택 (Mode 1/2 결정, ISO 1999 노화항 계산용) |

**1분 요약 레코드 (초안)**

```
MinuteRecord {
  user_id, device_id, output_id   // 누구의, 어느 기기의, 어느 이어폰
  minute_start_utc                // 분 단위 UTC 시각
  tier                            // A 자체재생 / B 시스템캡처 / C 레벨전용
  output_type                     // 이어폰·헤드폰 / 스피커(집계 제외) / 미상
  dose_eeh                        // 등에너지 선량 [Pa²h] — 기존 방식 (이중 게이지 마커)
  dose_kurt                       // 첨도 보정 선량 [Pa²h] — 등급 C면 null
  beta                            // 대표 첨도 — 등급 C면 null
  band_dose[19]                   // 1/3옥타브 대역별 [Pa²h] — 등급 C면 null
  volume_index                    // 그 기기의 볼륨 값 (기기 간 비교 금지)
  content_label                   // AI-3 범주
  calib_profile_id, calib_uncertainty_db
  schema_version, app_version
}
```

하루 3시간을 들어도 180개 레코드이므로 저장·전송 부담은 거의 없다.

### 14.3 병합 규칙

1. **합산은 에너지(Pa²h) 단위로 한다.** dB 값을 평균하거나 더하지 않는다.
2. **회복 적분기는 합친 타임라인 위에서 계산한다.** dF/dt = g·D(t) − F/τ는 선형이므로, 기기별 부담 D₁(t), D₂(t)의 합으로 적분한 결과는 기기별로 적분해서 더한 결과와 같다(중첩 원리). 따라서
   - 서버나 대시보드는 병합된 1분 레코드로 다시 계산하면 되고
   - 각 기기는 실시간 게이지를 위해 "다른 기기의 마지막 동기화 시점 F 값"을 그때부터 지금까지 감쇠시켜 자기 값에 더하면 된다.
3. **스피커 출력은 제외한다** (13.3절).
4. **동시 재생 겹침**: 같은 분에 두 기기에서 이어폰 출력이 기록되는 경우(예: 폰은 이어폰 연결 상태로 재생, 노트북도 같은 이어폰에 멀티포인트 연결). 한 사람이 동시에 두 이어폰을 꽂는 경우는 드무므로 **기본은 큰 값을 채택하고 겹침을 표시**한다(9절 #9). 이 경우 선형 중첩이 깨지므로 겹친 구간만 서버에서 다시 계산한다.
5. **시간**: 모두 UTC로 저장하고 화면에서만 현지 시각으로 보여 준다. 기기 시계 오차를 잡기 위해 서버 수신 시각도 함께 기록한다.
6. **오프라인 우선**: 기록은 기기에 먼저 쌓이고 연결될 때 올라간다. 레코드 식별자를 (device_id, minute_start)로 두면 같은 레코드를 여러 번 보내도 중복되지 않는다. 레코드는 추가만 하고 수정하지 않으므로 기기 간 충돌이 거의 없다.
7. **주간 7일 롤링 한도**(H.870)는 계정 단위로 계산한다.

### 14.4 다기기 합산과 원칙 3(상대 비교)의 충돌

기기와 이어폰마다 교정 오차가 다르다. 합산 선량의 불확실성은 가장 부정확한 기기 수준으로 커진다. 그래서:

- **합산은 "주간 허용 선량 대비 %"(표준 기준선량 대비) 용도로만 쓴다.**
- **기기 간 비교는 하지 않는다.** 볼륨 크리프(AI-2)는 (재생 기기 × 출력 장치) 조합 안에서만 본다. 노트북 볼륨 40과 폰 볼륨 40은 다른 값이다.
- 대역 지도는 등급 A·B 데이터로만 그리고, "이번 주 대역 지도는 전체 청취 시간의 62%를 기준으로 그렸습니다"처럼 범위를 표시한다.
- 화면에 **기기별 기여**(폰 62% · 노트북 30% · 패드 8%)와 각 기기의 측정 등급을 함께 보여 준다.

원칙 3은 "같은 사용자, 같은 기기 조합 안에서의 비교"로 유지되고, 계정 합산은 그 위에 표준 기준선 대비 비율만 더한다.

### 14.5 계정 · 개인정보

- **로그인 없이도 쓸 수 있어야 한다.** 로컬 전용 모드를 유지하고 동기화는 선택으로 둔다.
- **수집 최소화**: 이메일 또는 소셜 로그인만. 실명·학교·전화번호는 받지 않는다. 나이는 정확한 생년월일 대신 구간으로 받는다.
- **만 14세 미만**: 개인정보 처리에 법정대리인 동의가 필요하다(개인정보 보호법 제22조의2). 고등학생 위주라면 대부분 해당하지 않지만 중학생까지 대상으로 하면 필수다. 보호자 동의 절차를 만들거나 14세 미만에게는 동기화를 제공하지 않는다(9절 #10).
- **건강 관련 정보 해석 가능성**: 청취 노출 기록은 건강 관련 정보(민감정보, 같은 법 제23조)로 해석될 여지가 있다. 별도 동의를 받는 쪽으로 보수적으로 설계하고, 공개 전 지도교사·학교와 검토한다.
- **서버 위치**: 해외 리전을 쓰면 국외 이전 고지가 필요하다. 가능하면 서울 리전을 고른다.
- **삭제·내보내기**: 계정 삭제 시 서버 데이터 즉시 삭제, 내 기록 내보내기 버튼 제공.
- **iOS 로그인 규정**: iOS 앱에 구글·카카오 같은 외부 로그인을 넣으면 Apple 로그인 등 동등한 선택지를 요구받을 수 있다(App Store 심사 지침 4.8 — 확인 필요).
- **접근 제어**: 서버에서 "본인 레코드만 읽고 쓸 수 있다"는 규칙을 행 단위로 건다.

### 14.6 서버는 직접 만들지 않는다

학생 팀이 서버를 직접 운영하면 보안 사고 위험이 크다. 인증·DB·접근 규칙을 제공하는 관리형 백엔드를 쓴다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **Supabase** (권장) | PostgreSQL 기반이라 주간 집계·AI 학습용 데이터 추출을 SQL로 쉽게 함, 행 단위 접근 제어 내장 | 오프라인 업로드 대기열은 직접 구현 (⑥ 로컬 저장소가 이미 있어 간단) |
| Firebase | 오프라인 동기화 내장, 모바일 SDK 성숙 | 집계 쿼리가 불편, 읽기 횟수 과금 |

두 서비스 모두 무료 구간으로 시범 운영이 가능하고 서울 리전을 제공한다(가입 시 확인).

### 14.7 화면 반영

- **① 오늘**: "오늘 누적 47% (폰 62% · 노트북 30% · 패드 8%)"
- **⑤ 리포트**: 기기별 기여, 측정 등급 비율, 겹침 구간 표시
- **설정**: 내 기기 목록, 동기화 켜기/끄기, 내 데이터 내보내기·삭제, "서버에 올라가는 것 / 올라가지 않는 것" 표

## 15. 어떻게 시작할까 — 단계별 로드맵 (v3 신규)

**결론: 로그인 가능한 웹사이트로 시작하는 것은 좋다. 단 웹이 다른 앱의 소리를 백그라운드에서 듣게 하는 것은 불가능하므로(13.7절), 웹은 "계산 엔진 + 자체 재생 + 대시보드"로 만들고, 실생활 캡처는 2단계에서 안드로이드 수집기 앱이 맡는다.**

```
P0 가능성 실험 ─▶ P1 웹 프로토타입 ─▶ P2 수집기 앱 ─▶ P3 AI 레이어 ─▶ P4 공개 배포
   1~2주           3~5주              4~6주           데이터 수 주 후      대회 이후
                   (예선 영상 가능)    (실생활 데이터)  (AI-1, AI-2)
```

### Phase 0 — 가능성 실험 (1~2주, 버릴 코드)

목표: **13.1절 표의 "확인 필요" 칸을 직접 채운다.** 가장 짧은 실험용 코드로 진행한다.

| 실험 | 확인할 것 |
|---|---|
| 안드로이드 AudioPlaybackCapture | ① 앱별 캡처 가능 여부: 유튜브, 유튜브 뮤직, 스포티파이, 멜론, 넷플릭스, 틱톡, 인스타그램, 주요 게임 ② **화면 끈 채 30분 유지되는가** ③ 볼륨을 바꾸면 캡처 레벨도 바뀌는가 (볼륨 적용 전/후, 9절 #11) ④ 삼성 이퀄라이저 설정이 캡처 신호에 반영되는가 |
| 윈도우 loopback | 같은 앱 목록(브라우저·앱 버전), 볼륨 적용 전/후, 출력 장치 판별 |
| iOS (Mac이 있을 때) | HealthKit 헤드폰 노출 데이터를 읽을 수 있는가, 샘플 간격 |
| 장비 확인 | 팀·학교에 Mac이 있는가, 안드로이드 실험 기기 기종·버전 |

**산출물: "캡처 가능성 매트릭스"** (앱 × 플랫폼 × 화면 상태). 이후 모든 플랫폼 결정의 근거이자 보고서용 1차 자료.

### Phase 1 — 웹 프로토타입 (3~5주)

1. **공통 코어 라이브러리** (TypeScript): ②③④⑤를 순수 함수로 만든다. 입력은 PCM 프레임, 출력은 특징값. 브라우저 오디오 API에 의존하지 않는다.
2. **골든 테스트 벡터** (16.2절): 기준 WAV + 기대 출력. 이 단계에서 V1·V3·V4 검증을 끝낸다.
3. **웹 앱**: 자체 재생 모드(데모곡, 파일 업로드) + 5개 탭. 「10년 뒤 이 노래」는 웹에서 완전히 동작한다.
4. **로그인 + 1분 레코드 동기화**를 이 단계에서 붙인다. 데이터는 아직 자체 재생 세션뿐이지만 구조를 먼저 검증한다.
5. (선택) 데스크톱 Chrome 공유 세션으로 등급 B 맛보기.

→ **대회 예선 영상을 만들 수 있는 상태.**

### Phase 2 — 실생활 데이터 수집기 (4~6주)

| 순서 | 수집기 | 내용 |
|---|---|---|
| 1 | **안드로이드** | Kotlin으로 캡처 + 1초 특징 추출(코어의 ②③만 이식) + 1분 레코드 업로드. 화면은 최소(상태, 동의)로 두고, 본 화면은 웹 대시보드 또는 앱 안의 웹뷰 |
| 2 | 윈도우 데스크톱 | Electron 트레이 앱, 웹 코어 그대로 사용 |
| 3 | iOS·iPadOS | HealthKit 레벨 수집 (등급 C) |

모든 수집기는 **골든 테스트 벡터를 통과해야 배포한다** (V8).

### Phase 3 — AI 레이어

AI-1(궤적 예측)과 AI-2(볼륨 크리프)는 **수 주치 실생활 데이터가 있어야** 학습·검증할 수 있다. Phase 2가 늦어지면 AI도 늦어진다. **팀원 본인 기기에서 먼저 수집을 시작한다** (팀원 데이터도 동의서를 받고 사용).

### Phase 4 — 공개 배포 (공익 서비스)

개인정보 처리방침, 보호자 동의 절차, 스토어 심사, 의료기기·웰니스 표현 검토.

## 16. 코드 구조와 플랫폼 이식 전략 (v3 신규)

### 16.1 "하나 만들어 놓고 AI에게 iOS·안드로이드용으로 바꿔 달라"고 하면 되는가?

**절반은 된다.**
- **화면과 계산 로직**은 AI가 다른 언어·플랫폼으로 잘 옮긴다.
- **소리 수집 부분은 번역이 아니라 새로 설계해야 한다.** OS마다 방식 자체가 다르기 때문이다(13절). 안드로이드는 화면 녹화 권한 + 포그라운드 서비스, iOS는 HealthKit 또는 방송 확장, 윈도우는 loopback이다. 이 프로젝트의 기술적 난이도는 대부분 여기에 있다.
- **AI가 옮긴 코드가 맞는지 증명할 장치가 필요하다.** 그것이 골든 테스트 벡터다(16.2절). 이것이 없으면 "안드로이드 버전 숫자가 웹이랑 다른데 어디가 틀렸지?"에 답할 수 없고, 0절의 역추적 가능성이 무너진다.

### 16.2 골든 테스트 벡터

"이 입력을 넣으면 이 숫자가 나와야 한다"는 정답 묶음이다. 모든 구현(웹·안드로이드·데스크톱·iOS)이 같은 파일을 통과해야 한다.

| 테스트 WAV | 기대 성질 |
|---|---|
| 1 kHz 사인파, 여러 레벨 | β ≈ 1.5, 대역 하나에 에너지 집중, 레벨 비례 |
| 가우시안 백색잡음 | β ≈ 3 → 첨도 보정 무효 (V3) |
| 임펄스열 (총소리 흉내) | β ≫ 3 → 보정 배율 > 1 |
| 핑크 노이즈 | 1/3옥타브 대역 에너지가 거의 고르게 분포 |
| 무음 | 선량 0, F(t) 다중지수 감쇠 (V4) |
| 실제 음악 클립 몇 개 | 웹 기준 구현의 출력을 기대값으로 고정 |

기대값은 웹(TS) 기준 구현 + Python 독립 계산 두 가지로 교차 확인해서 만든다.

### 16.3 플랫폼별 브랜치 대신 한 저장소의 폴더로

플랫폼마다 브랜치를 따로 두는 방식(android 브랜치, ios 브랜치)은 **권장하지 않는다.** 계산식 하나를 고치면 모든 브랜치에 같은 수정을 반복해야 하고, 금방 서로 다른 프로그램이 된다. 한 저장소 안에 폴더로 나눈다.

```
safeear/
├─ core/                 # 공통 계산 (TypeScript) — ②③④⑤, 오디오 API 의존 없음
├─ core-kotlin/          # ②③ 프레임 특징 추출만 Kotlin으로 이식 (안드로이드 백그라운드용)
├─ test-vectors/         # 골든 WAV + 기대 출력 JSON — 모든 구현이 통과해야 함
├─ web/                  # 대시보드 + 자체 재생 모드 (Phase 1)
├─ collector-android/    # 안드로이드 수집기 (Phase 2)
├─ collector-desktop/    # 윈도우 수집기 (Electron)
├─ collector-ios/        # HealthKit 연동
├─ server/               # DB 스키마, 접근 규칙
└─ docs/                 # 이 계획서, 캡처 가능성 매트릭스
```

브랜치는 **기능 단위**(예: 첨도 보정, 동기화)로 만들어 작업하고 main에 합친다.

### 16.4 왜 "1초 특징 추출"만 네이티브로 옮기는가

- 모바일에서 화면이 꺼지면 OS가 웹뷰·자바스크립트를 멈춘다. 그래서 **소리 수집과 1초 특징 계산(②③)은 네이티브 코드**여야 한다.
- 1분 레코드 이후의 계산(④ F(t), ⑤ ISO 1999, ⑧ AI, ⑦ UI)은 실시간일 필요가 없으므로 **공통 TypeScript 한 벌**로 충분하다.
- 옮기는 범위가 작을수록 검증할 범위도 작아진다.

### 16.5 앱 프레임워크 선택지

| 방식 | 장점 | 단점 |
|---|---|---|
| **웹 + Capacitor** (권장) | Phase 1 웹 코드를 그대로 앱으로 감쌈. 팀의 HTML/JS 경험 활용 | 캡처 부분은 Kotlin/Swift 플러그인을 직접 작성 |
| React Native / Flutter | 앱다운 화면, 큰 생태계 | 웹 코드 재작성, 새로 배워야 함 |
| 플랫폼별 완전 네이티브 | 성능·제어 최고 | 플랫폼마다 따로 만들어야 해 인력이 부족 |

데스크톱은 **Electron**(전부 JS, 윈도우 시스템 오디오 수집이 비교적 쉬움)을 권장한다. 더 가벼운 Tauri도 있지만 Rust를 배워야 한다.

## 17. iOS·iPadOS에서 최대한 가능하게 하는 방안 (v3.1 신규)

### 17.0 출발점 — 막힌 것과 열린 것

| 막혀 있는 것 | 열려 있는 것 |
|---|---|
| 다른 앱 소리 파형을 **사용자 동의 없이 자동으로** 받기 | **HealthKit 헤드폰 노출 레벨** (+ 새 데이터가 생기면 앱을 깨우는 백그라운드 전달) |
| 앱이 아무 목적 없이 백그라운드에 계속 살아 있기 | **ScreenCaptureKit (iOS 27+)** — 사용자가 측정을 시작하면 다른 앱 소리를 받고, 캡처하는 동안 백그라운드 유지 |
| | **ReplayKit 방송 (iOS 26 이하)** — 같은 목적의 구형 방식, 불안정 |
| 다른 앱이 지금 무엇을 재생 중인지 읽기 | **앱 안에서 직접 재생하는 소리** (DRM 없는 파일·스트림) |
| 시스템 볼륨을 계속 읽기 | **청취 기록 외부 연동** (Apple Music, Spotify, Last.fm) |
| | **단축어 자동화** — "특정 앱이 열리면 SafeEar에 기록" |
| | **위젯 · 잠금화면 실시간 현황(Live Activity) · 알림** |
| | 사용자에게 **iOS 설정을 안내**하는 것 (블루투스 기기 유형, 큰 소리 줄이기) |

**핵심 아이디어**: 13.3절에서 "크기"와 "모양"을 나눴다. iOS에서는

- **크기**는 HealthKit이 거의 항상 준다.
- **모양**은 실시간 파형에서 얻을 수 없으므로 두 갈래로 얻는다.
  1. **사용자가 켠 동안 실측한다** — 정밀 측정 세션 (iOS 27+ ScreenCaptureKit, ≤26 ReplayKit — 17.8절)
  2. **무엇을 들었는지 알아낸 뒤, 그 콘텐츠의 모양을 따로 구한다** — 청취 기록 + 곡 미리듣기 음원 / 콘텐츠 유형 대표 모양

### 17.1 방안 목록

### 17.2 각 방안의 세부 사항과 주의점

**① HealthKit 헤드폰 노출**
- Apple이 헤드폰 출력 레벨을 dB(A)로 기록하고, 앱은 읽기 권한을 받아 가져온다.
- 백그라운드 전달을 켜면 새 샘플이 기록될 때 앱이 잠깐 깨어나 F(t)를 갱신하고 위젯·알림을 업데이트할 수 있다. **전달 지연·빈도는 실험으로 확인한다.**
- 샘플에는 기록한 기기(어느 헤드폰인지) 정보가 붙는다(확인 필요). 14.2절 레코드의 `output_id`로 쓴다.
- **iPad에서도 헤드폰 레벨이 기록되는지는 반드시 확인한다.** 기록되지 않으면 iPad는 ③④⑥⑦ 조합으로 내려간다.
- 비애플 이어폰은 볼륨 기반 추정치라 오차가 크다. 교정 불확실성 칸에 반영한다.

**② 블루투스 기기 유형 설정**
- 비애플 무선 이어폰은 iOS 블루투스 설정에서 기기 유형을 "헤드폰"으로 지정해야 헤드폰 노출로 집계되는 경우가 있다(확인 필요). 온보딩에 "이어폰 등록하기" 단계로 넣는다.

**③ 정밀 측정 세션** — 상세 검토는 **17.8절**
- **iOS 27+**: 공식 ScreenCaptureKit을 쓴다. 화면 잠금 시에도 유지되면 "청취 세션 하나 = 시작 한 번"으로 쓸 수 있어, 상시 측정에 가까워진다.
- **iOS 26 이하**: ReplayKit 방송. 화면 잠금 시 꺼진다는 보고가 있어 "게임할 때 30분" 같은 짧은 **표본 측정**으로만 쓰고, D 등급 추정을 보정하는 데 활용한다.
- 두 방식 모두 화면 영상은 받지 않거나 **즉시 버리고 저장하지 않는다.** 온보딩과 근거 시트에 명시한다.

**④ 자체 재생**
- 내 음악 파일(파일 앱), 팟캐스트 RSS, DRM 없는 인터넷 라디오는 앱 안에서 재생하며 파형 전체를 분석할 수 있다.
- Apple Music·Spotify·유튜브는 앱 안에서 재생해도 **파형에 접근할 수 없다**(DRM 또는 원격 제어 방식).
- 「10년 뒤 이 노래」(6.3절)는 이 방식으로 iOS에서도 완전히 동작한다.

**⑤ 청취 기록 연동**
- **Apple Music**: MusicKit으로 최근 재생 곡을 가져올 수 있다. 다만 **정확한 재생 시각이 없을 수 있어**(확인 필요) HealthKit 레벨 구간과 곡 길이로 시간을 맞춘다. 우리 앱이 켜져 있는 동안에는 지금 재생 중인 곡도 알 수 있다.
- **Spotify**: 최근 재생 API는 재생 시각을 준다. 다만 2024~2025년 정책 변경으로 미리듣기 링크·오디오 특징 API가 신규 앱에서 막혔고, 개인·소규모 앱은 **허용 사용자 수가 적은 개발 모드에 묶일 수 있다**(확인 필요). 시범 운영(팀원·학급) 규모에서는 쓸 수 있을 가능성이 있다.
- **Last.fm**: 스포티파이 등에서 자동 기록(스크로블)하는 사용자라면 재생 시각까지 포함된 기록을 받을 수 있다.
- 곡은 국제표준녹음코드(ISRC)로 식별해 ⑥의 미리듣기 음원과 맞춘다.

**⑥ 곡 미리듣기 기반 모양 추정**
- Apple(iTunes 검색)이나 Deezer 등이 제공하는 30초 미리듣기 음원을 분석해 그 곡의 β·대역 분포를 구한다.
- **크기는 HealthKit, 모양은 미리듣기**라는 분리가 13.3절 설계와 그대로 맞물린다. 스트리밍 서비스의 음량 평준화(Sound Check 등) 때문에 미리듣기의 크기는 실제와 다르지만, 크기는 쓰지 않으므로 상관없다.
- **한계**: 30초 구간이 곡 전체를 대표하지 않을 수 있다. 사용자 EQ 설정은 반영되지 않는다. 음악만 가능하고 유튜브·게임은 안 된다.
- 결과는 **D 등급**으로 표시하고, V11(8절)에서 구한 오차 범위를 함께 보여 준다.
- 미리듣기를 분석 목적으로 써도 되는지 각 서비스 약관을 확인한다(9절 #13). 곡 단위 결과(β, 대역 19개 값)만 캐시하고 음원 자체는 저장하지 않는다.

**⑦ 단축어 자동화**
- iOS 단축어의 "앱이 열릴 때" 개인 자동화로 SafeEar의 기록 동작(App Intent)을 실행하게 한다. 유튜브, 틱톡, 게임 등을 언제 열었는지 기록된다.
- HealthKit 레벨 구간과 합치면 **"이번 주 부담의 40%는 유튜브 사용 중에 발생"** 같은 콘텐츠 귀속(AI-3의 목표)을 파형 없이 얻는다.
- 사용자가 자동화를 직접 설정해야 하므로 설정 안내 화면이 필요하다. iOS 버전에 따라 실행 시 확인 알림이 뜨는지 확인한다.
- Screen Time 관련 API(FamilyControls, DeviceActivity)는 앱 사용 데이터를 앱 밖으로 꺼낼 수 없게 설계되어 있고 별도 권한 승인이 필요해, 이 목적에는 단축어가 현실적이다.

**⑧ 콘텐츠 유형 대표 모양**
- 팀이 실험실 도구(⑫)와 안드로이드 실측(B)으로 "유튜브 일반 영상", "숏폼", "FPS 게임", "리듬 게임", "팟캐스트" 등 유형별 β·대역 분포를 미리 측정해 표로 만든다.
- ⑦로 앱을 알면 그 유형의 대표 모양을 D 등급으로 적용한다. 분산(오차 범위)을 함께 저장한다.

**⑨ Apple Watch 주변 소음**
- 워치가 기록하는 주변 소음 레벨을 HealthKit으로 읽어 AI-2(볼륨 크리프)의 "지하철·버스 때문에 볼륨을 올렸다" 교란 변수로 쓴다.

**⑩ "큰 소리 줄이기" 안내**
- iOS에는 헤드폰 출력이 설정한 dB를 넘지 않게 하는 기능이 있다. SafeEar가 직접 볼륨을 조절할 수는 없지만, **"Mode 2 기준에 맞춰 75~80 dB로 설정해 보세요"**라고 안내할 수 있다.
- H.870의 "경고 후 볼륨 자동 감소" 요구(3.5절)를 iOS에서 **사용자 설정으로 대신 충족**하는 경로다. 측정이 아니라 개입이므로 효과는 AI-2 볼륨 추세로 따로 본다.

**⑪ 위젯 · Live Activity · 알림**
- iOS 앱은 백그라운드에 상주할 수 없으므로 "앱을 열지 않아도 보이는 화면"이 중요하다. ①의 백그라운드 전달로 갱신된 F(t)를 잠금화면 위젯과 알림("지금 30분 쉬면 47%까지 내려갑니다")으로 보여 준다.

**⑫ 실험실 도구**
- 맥은 AirPlay 수신과 iPhone 미러링으로 아이폰 소리를 맥에서 재생할 수 있다. 이 소리를 Core Audio Tap(13.1절)으로 캡처하면 **iOS 앱 소리를 연구용으로 측정**할 수 있다(보호 콘텐츠는 막힐 수 있음).
- 측정용 마이크 + 인공 귀(커플러)로 아이폰·이어폰 조합의 볼륨 → dB SPL 곡선을 재면 9절 #3(SPL 교정)에도 쓸 수 있다.

**⑬ AUv3 플러그인**
- 음악 제작 앱 안에서만 동작하므로 일반 청취에는 쓸모가 적다. 악기 연습·작곡하는 학생을 위한 부가 기능 정도로만 남긴다.

### 17.3 조합하면 어떻게 되나 — iOS 사용자의 하루 예시

| 상황 | 쓰이는 방안 | 크기 | 모양 | 귀속 |
|---|---|---|---|---|
| 등굣길 스포티파이 40분 | ①②⑤⑥ | HealthKit | 곡별 미리듣기 (D) | 곡·아티스트 |
| 쉬는 시간 유튜브 20분 | ①⑦⑧ | HealthKit | "유튜브 일반" 대표 모양 (D) | 유튜브 |
| 저녁 게임 1시간, 정밀 측정 켬 | ①③ | HealthKit | 실측 (B) | 게임 (실측 분류) |
| 밤 다운받은 음악 파일, SafeEar로 재생 | ④ | 앱이 앎 | 실측 (A) | 곡 |
| 주말 노트북으로 강의 | 윈도우 수집기 (13.6절) | 추정 | 실측 (B) | 앱별 |

→ **에너지 선량, F(t), 장기 예측, 사전 경고는 거의 모든 시간에 동작한다.** 첨도·대역 지도는 실측(A·B)과 추정(D)이 섞이며, 화면에서 비율을 보여 준다(예: "이번 주 대역 지도: 실측 25% · 추정 60% · 정보 없음 15%").

### 17.4 한계를 연구 기여로 바꾸기 — 안드로이드 실측으로 iOS 추정을 검증

안드로이드에서는 같은 곡·같은 앱의 실제 파형을 받을 수 있다(B). 그래서

1. 안드로이드 사용자가 들은 곡의 **실측 β·대역**과 **같은 곡 미리듣기로 구한 추정값**을 비교한다 → ⑥의 오차 분포
2. 안드로이드에서 유튜브·게임을 들을 때의 실측값과 **유형 대표 모양**을 비교한다 → ⑧의 오차 분포
3. 이 오차를 iOS 화면의 오차 범위로 그대로 쓴다 (8절 V11)

"iOS에서는 측정할 수 없다"로 끝내지 않고 **"iOS에서는 이 정도 오차로 추정할 수 있다는 것을 실측으로 검증했다"**는 결과가 된다. 원칙 2(관찰은 단언, 원인은 단언하지 않음)와 근거 시트(6.5절)의 정신에도 맞다.

### 17.6 필요한 준비물

- 실험실 도구(⑫)용 맥, 측정용 마이크(선택)

### 17.8 정밀 측정(③)은 정말 가능한가 — 2026.10 조사 결과 (v3.2)

#### 17.8.1 결론

| iOS 버전 | 판정 | 근거 수준 |
|---|---|---|
| **iOS·iPadOS 27 이상** | **가능성 높음.** 공식 API로 다른 앱 소리를 받고, 백그라운드에서도 계속 받을 수 있다 | 애플 공식 문서 + 개발자 포럼 실사용 보고. **화면 잠금 시 동작과 앱별 결과는 미확인** |
| **iOS·iPadOS 26 이하** | **가능하지만 짧은 세션용.** 화면 잠금·전화 수신 시 꺼진다는 보고가 있다 | 개발자 보고 (비공식) |

#### 17.8.2 확인된 사실

**애플 공식 문서 (developer.apple.com, 2026.10 확인)**
- ScreenCaptureKit의 지원 플랫폼에 **iOS 27.0, iPadOS 27.0**이 추가되었다. 문서는 "ScreenCaptureKit이 화면 스트리밍·미러링에서 ReplayKit을 대체하며, 방송 확장 프로그램은 더 이상 필요 없다"고 적고 있다.
- 소리 캡처 옵션 `capturesAudio`와 소리 출력 유형 `SCStreamOutputType.audio`가 iOS 27에서 제공된다.
- 백그라운드 실행 모드에 **`screen-capture`("앱이 백그라운드에서 화면 콘텐츠를 캡처·전송")**가 iOS·iPadOS용으로 추가되었다.
- 콘텐츠 선택은 시스템이 띄우는 **공유 선택창(SCContentSharingPicker)**을 쓰도록 권장한다. macOS처럼 앱이 화면·앱 목록을 직접 조회하는 기능은 iOS에 없다. 즉 **사용자가 선택창에서 고르는 것이 유일한 시작 방법**이다.
- 기존 `RPBroadcastSampleHandler`(방송 확장)는 iOS 27.0에서 **지원 중단 예정(deprecated)**으로 표시되었다.

**애플 개발자 포럼 보고 (공식 답변이 아닌 실사용 보고)**
- iOS 27.0 실기기(iPhone 15 Pro Max)에서 **애플 뮤직 앱을 캡처 대상으로 골랐을 때 실제 소리가 PCM으로 들어왔다**(스테레오, 48 kHz, 32비트 실수). 인터넷 라디오(SomaFM)도 정상이었다.
- 같은 환경에서 **Zoom·Teams 통화 소리는 형식만 맞고 값이 전부 0**이었다. 통화는 원래 집계 대상이 아니므로(13.8절) SafeEar에는 문제가 되지 않는다.
- 앱이 백그라운드로 가면 `screen-capture` 모드를 선언하지 않은 경우 캡처가 오류(-3824)로 종료된다. 무음 재생으로 앱을 살려 두는 방법으로는 막을 수 없었다고 한다.
- 2026년 8월에는 App Store Connect가 `screen-capture` 값을 거부했지만, **애플 DTS 엔지니어가 "해결되었다"고 답했고 작성자도 업로드 검증을 통과했다고 확인**했다. 앱스토어 배포 경로는 열린 것으로 보인다.
- 자기 앱 소리를 캡처에서 빼는 옵션(`excludesCurrentProcessAudio`)이 iOS 27.0에서 동작하지 않는다는 보고가 있다. SafeEar가 「10년 뒤 이 노래」를 재생하는 동안에는 캡처 분석을 멈춰서 이중 집계를 피한다.
- 화면 프레임은 최대 60 fps로 들어온다는 보고가 있다. 소리만 쓰므로 상관없다.

**iOS 26 이하 (ReplayKit)**
- 화면 잠금이나 전화 수신 시 방송이 자동 종료된다는 SDK 업체 문서가 있다(Tencent Cloud).
- 확장 프로그램 메모리 한도는 약 50MB로 알려져 있다(공식 문서 없음, 업체 문서·포럼 보고).

#### 17.8.3 "매번 직접 켠다"는 것의 실제 화면 흐름

**iOS 27 이상**

```
① SafeEar 앱을 열고 「측정 시작」을 누른다
② iOS가 공유 선택창을 띄운다
     ┌───────────────────────────────┐
     │  무엇을 공유할까요?             │
     │   ○ 이 앱                      │
     │   ○ 다른 앱 (예: 음악, 유튜브)   │
     │   ● 전체 화면  ← SafeEar 안내    │
     │   마이크  [끔]                  │
     │          [ 공유 시작 ]          │
     └───────────────────────────────┘
③ 「공유 시작」을 누르면 상단에 캡처 중 표시가 뜬다
④ 홈으로 나가 평소처럼 음악·유튜브·게임을 쓴다
   → SafeEar는 백그라운드에서 소리만 분석 (screen-capture 모드)
⑤ 끝: 상단 캡처 표시를 눌러 중지, 또는 SafeEar에서 「측정 종료」
```

- 선택창 문구와 배치는 iOS가 정한다. 위 그림은 개발자 문서에 나온 선택지(이 앱 · 다른 앱 · 전체 화면 · 마이크)를 옮긴 것이고, **실제 화면은 실기기에서 확인한다.**
- **"전체 화면"을 골라야 한다.** "다른 앱"으로 특정 앱 하나만 고르면, 사용자가 음악에서 유튜브로 옮겨 갔을 때 유튜브 소리는 들어오지 않을 가능성이 높다(확인 필요). 온보딩에서 "전체 화면을 고르세요. 화면은 저장하지 않습니다"를 안내한다.
- 선택창이 열린 채 60초가 지나면 자동으로 닫힌다(LiveKit SDK 문서).

**iOS 26 이하**

```
방법 A: SafeEar 앱의 「측정 시작」 → 「화면 브로드캐스트」 창 → SafeEar 선택 → 「브로드캐스트 시작」 → 3초 카운트다운
방법 B: 제어센터 → 화면 기록 버튼 길게 누르기 → SafeEar 선택 → 「브로드캐스트 시작」
```

**"매번"의 정확한 뜻 — 다시 켜야 하는 경우**

| 상황 | iOS 27+ | iOS ≤26 |
|---|---|---|
| 사용자가 캡처 표시를 눌러 중지 | 다시 켜야 함 | 다시 켜야 함 |
| **화면 잠금 / 화면 꺼짐** | **확인 필요 — 가장 중요한 실험** | 꺼진다는 보고 있음 |
| 전화 수신 | 확인 필요 | 꺼진다는 보고 있음 |
| 휴대폰 재시작, SafeEar 강제 종료 | 다시 켜야 함 (사실상 확실) | 다시 켜야 함 |
| 시스템이 메모리 부족으로 앱 종료 | 다시 켜야 함 | 다시 켜야 함 |

→ iOS 27에서 화면 잠금 후에도 유지된다면, **아침에 한 번 켜 두면 하루 종일 측정**되는 수준까지 갈 수 있다. 유지되지 않는다면 "화면을 켠 채 쓰는 게임·영상 시간"만 실측되고, 화면을 끈 채 듣는 음악은 HealthKit 레벨(C)과 대리 추정(D)으로 채운다.

**켜는 부담을 줄이는 방법**
- 측정이 꺼지면 **알림으로 다시 켜기를 권한다.** 이어폰 연결 이벤트는 앱이 꺼져 있으면 받기 어렵다. 대신 HealthKit에 새 헤드폰 노출 기록이 생기는 것을 신호로 "지금 듣고 계시네요. 정밀 측정을 켤까요?"를 보낸다.
- 잠금화면 위젯·제어센터 버튼(iOS 18+ 제어 위젯)에 「측정 시작」을 둔다. 단 이 버튼은 SafeEar를 열고 선택창을 띄우는 데까지만 하고, 선택은 사용자가 직접 해야 한다.
- 단축어 자동화(17.1절 ⑦)로 "이어폰이 연결되면 SafeEar 열기"를 설정하게 한다(단축어의 블루투스 연결 트리거 사용 가능 여부 확인 필요).

#### 17.8.4 남은 위험

| 위험 | 영향 | 대응 |
|---|---|---|
| 화면 잠금 시 캡처 종료 | 음악 청취 대부분을 놓침 | C·D 등급으로 보완, 화면 켠 시간만 B |
| 앱별 차단 (넷플릭스 등 보호 영상, 일부 게임) | 해당 앱 시간만 실측 불가 | 앱별 결과를 매트릭스로 기록, 해당 시간은 C·D |
| 전체 화면 캡처에 대한 사용자 거부감 | 측정 시작률 하락 | 화면 출력 자체를 등록하지 않는 구성 시도(소리만 받기), 안내 문구, 근거 시트 |
| 앱 심사 | 출시 지연 | 사용 목적 설명 문구(`NSScreenCaptureUsageDescription`), 심사 메모에 "소리 분석만, 저장·전송 없음" 명시 |
| iOS 27 미만 사용자 | 정밀 측정 불가 또는 불안정 | ReplayKit 짧은 세션, C·D 등급 |
| 배터리 | 장시간 측정 시 소모 | 1초 FFT만 상시, 무거운 분류 모델은 간격 실행. 실측해서 보고 |
| iOS 27 초기 버그 (포럼에 다수 보고) | 동작 불안정 | iOS 27.x 업데이트마다 재시험 |

#### 17.8.6 계획에 주는 영향

- iOS가 "레벨만 되는 플랫폼"에서 **iOS 27 이상은 안드로이드에 가까운 플랫폼**으로 올라간다. 단 실험 1(화면 잠금)의 결과에 따라 "하루 종일"인지 "화면 켠 시간만"인지가 갈린다.
- 17.1절의 ⑤⑥⑧(청취 기록·미리듣기·유형 대표 모양)은 **iOS 26 이하 사용자와 화면 꺼진 시간을 위한 보완책**으로 유지한다.
- 대회 시연은 iOS 27 iPhone 한 대와 Mac(Xcode)만 있으면 앱스토어 출시 없이 개발 빌드로 가능하다.

### 17.9 iOS·iPadOS 27+ 동작 계획 — 사용자 입장에서 (v3.3)

17.8절의 조사 결과를 **사용자가 실제로 겪는 흐름**으로 다시 정리한 것이다. ✅는 문서·보고로 확인된 것, ❓는 17.8.5 실험으로 확인할 것이다.

#### 17.9.1 한 줄 요약

> 측정을 한 번 켜 두면 **특정 앱 하나가 아니라 휴대폰에서 나오는 거의 모든 앱 소리**를 분석한다. 다만 **켤 때마다 사용자가 시스템 창에서 직접 확인해야 하고**, 화면 잠금 후에도 유지되는지가 사용 편의를 결정한다(❓).

#### 17.9.2 앱 하나만 되는가?

측정을 시작하면 iOS의 공유 선택창이 뜨고 사용자가 범위를 고른다.

| 선택 | 분석되는 소리 | SafeEar 방침 |
|---|---|---|
| **전체 화면** | 휴대폰에서 나오는 거의 모든 앱 소리. 음악 → 유튜브 → 게임으로 옮겨 가도 계속 들어옴 | **이것을 고르도록 안내** |
| 다른 앱 (예: 음악 앱만) | 그 앱 소리만 들어올 가능성이 높음 ❓ | 비권장 |
| 이 앱 | SafeEar 자체 소리만 | 사용 안 함 |

전체 화면이어도 빠지는 소리:
- **통화·영상회의(Zoom·Teams 등)**: 0으로 들어온다는 보고 ✅ → 원래 집계 대상이 아니므로 문제없음 (13.8절)
- **보호 영상(넷플릭스 등), 일부 게임**: ❓ → 앱별 매트릭스로 확인. 애플 뮤직은 정상 수신 보고 ✅

#### 17.9.3 켜는 법

```
① SafeEar 열기 → 「측정 시작」
② iOS 공유 선택창 → 「전체 화면」 선택, 마이크는 끈 채로 → 「공유 시작」
③ 화면 상단에 캡처 중 표시
④ 홈으로 나가 평소처럼 음악·유튜브·게임 사용
   (SafeEar를 열어 둘 필요 없음 — screen-capture 백그라운드 모드 ✅)
```

- **②는 매번 사용자가 직접 눌러야 한다 ✅.** 앱이 자동으로 시작하거나 "다음부터 묻지 않기"를 고르는 방법은 iOS에 없다. 애플이 개인정보 보호를 위해 일부러 막아 둔 부분이다.
- 선택창을 열어 둔 채 60초가 지나면 자동으로 닫힌다 (LiveKit SDK 문서).
- ①까지 가는 길을 줄이는 방법:

| 방법 | 동작 | 상태 |
|---|---|---|
| 잠금화면·제어센터의 「측정 시작」 버튼 | 누르면 SafeEar가 열리며 선택창 표시 | 제어 위젯은 iOS 18+ 기능 ✅, 바로 선택창까지 이어지는지 ❓ |
| "지금 듣고 계시네요" 알림 | 건강 앱에 새 헤드폰 기록이 생기면 알림 → 탭하면 ① | 백그라운드 전달 지연 ❓ |
| 단축어 자동화 | 이어폰 연결 시 SafeEar 열기 | 블루투스 연결 트리거 사용 가능 여부 ❓ |

#### 17.9.4 꺼지는 경우

| 상황 | 결과 | 상태 |
|---|---|---|
| 상단 캡처 표시를 눌러 중지 / 앱에서 「측정 종료」 | 꺼짐 → 다시 켜야 함 | ✅ |
| 휴대폰 재시작, SafeEar 강제 종료, 메모리 부족으로 앱 종료 | 꺼짐 → 다시 켜야 함 | ✅ (사실상 확실) |
| **화면 잠금·화면 꺼짐** | ❓ **가장 중요한 실험 (17.8.5 #1)** | ❓ |
| 전화 수신 | ❓ | ❓ |

측정이 꺼지면 SafeEar는 꺼진 시각을 기록하고(14.2절 레코드에 "미측정" 구간), 다음에 앱을 열 때나 알림으로 다시 켜기를 권한다.

#### 17.9.5 화면 잠금 실험 결과에 따른 두 시나리오

| | 시나리오 1: 잠가도 유지 | 시나리오 2: 잠그면 꺼짐 |
|---|---|---|
| 켜는 빈도 | **아침에 한 번** (재시작 전까지) | 화면을 켜고 쓸 때마다 |
| 실측되는 시간 | 하루 대부분 | 영상·게임처럼 **화면을 켜고 쓰는 시간만** |
| 화면 끄고 듣는 음악 | 실측 (B) | 건강 앱 레벨(C) + 청취 기록 기반 추정(D) |
| 안드로이드와 비교 | 거의 동등 | 영상·게임은 동등, 음악은 추정 |
| 계획 변경 | iOS 정밀 측정을 P2로 앞당김 | 17.1절 ⑤⑥⑧(청취 기록·미리듣기·유형 대표 모양)의 중요도 상승 |

#### 17.9.6 측정이 켜졌을 때와 꺼졌을 때

| 기능 | 측정 켜짐 | 측정 꺼짐 |
|---|---|---|
| 소리 크기 · 에너지 선량 · 회복 게이지 F(t) · 10년 예측 · 사전 경고 | ✅ | ✅ **건강 앱 레벨로 계속 계산** |
| 첨도 β | 실측 (B) | 추정 (D, 점선) 또는 "측정 불가" |
| 1/3옥타브 대역 지도 (코코 껍데기) | 실측 (B) | 추정 (D, 점선) 또는 공백 |
| 콘텐츠 분류 (AI-3) | 소리로 분류 | 단축어·청취 기록으로 일부 |
| 볼륨 크리프 (AI-2) | 레벨 + 실측 | 레벨만 |

→ **측정을 꺼도 앱의 핵심 경고 기능은 계속 동작한다.** 측정은 정밀도를 올리는 기능이지 앱이 동작하기 위한 조건이 아니다. 온보딩에서도 그렇게 설명한다 ("안 켜도 기본 기능은 작동해요. 켜면 더 정확해져요").

#### 17.9.7 사용자에게 알려야 할 것 (온보딩 · 근거 시트)

- **"화면 녹화가 아닙니다."** 전체 화면을 고르지만 화면 영상은 받지 않거나 즉시 버린다. 소리도 저장하지 않고, 1초마다 숫자 몇 개(크기, 첨도, 19개 대역 에너지)로 바꾼 뒤 원본은 버린다 (14.2절).
- 캡처 중에는 화면 상단에 표시가 계속 보인다. 이는 iOS가 강제하는 것이며 끌 수 없다.
- 마이크는 쓰지 않는다. 선택창에서 마이크를 끈 채로 두라고 안내한다.
- SafeEar 안에서 「10년 뒤 이 노래」를 재생하는 동안에는 자기 소리가 측정에 섞이지 않도록 **분석을 잠시 멈춘다** (iOS 27.0에서 자기 소리 제외 옵션이 동작하지 않는다는 보고, 17.8.2절).
- 배터리 소모는 실측 후 안내한다 (17.8.5 #6).

#### 17.9.8 화면 반영 (6.4절 보완)

| 화면 | 추가 요소 |
|---|---|
| **① 오늘** | 상단에 측정 상태 배지: 「● 정밀 측정 중 (2시간 13분)」 / 「○ 기본 측정 — 켜면 더 정확해져요 [측정 시작]」 |
| **① 오늘** | 오늘 청취 중 실측 비율: "실측 64% · 추정 22% · 레벨만 14%" |
| **② 귀 지도** | 코코 껍데기에서 실측 구간은 실선, 추정 구간은 점선 |
| **⑤ 리포트** | 요일×시간대 히트맵에 측정 등급(A/B/C/D) 겹쳐 보기 |
| **설정** | "정밀 측정 안내 다시 보기", 제어센터 버튼 추가 방법, 단축어 자동화 설정 방법 |
| **온보딩** | 선택창 화면을 미리 보여 주고 "「전체 화면」 → 「공유 시작」"을 가리키는 안내 (실기기 화면 확인 후 제작) |

#### 17.9.9 iPad와 iOS 26 이하

| | 동작 |
|---|---|
| **iPadOS 27+** | iPhone과 같은 방식. 단 **iPad에서도 건강 앱에 헤드폰 레벨이 쌓이는지** ❓ — 쌓이지 않으면 측정을 꺼 둔 시간은 아무것도 기록되지 않으므로, iPad는 "쓸 때 측정 켜기"를 더 강하게 권한다 |
| **iOS·iPadOS 26 이하** | 「브로드캐스트 시작」 방식(ReplayKit)만 가능. 화면 잠금·전화 수신 시 종료 보고 → "게임할 때 30분" 같은 짧은 표본 측정용. 나머지는 C·D 등급 |

#### 17.9.10 정리표

| 질문 | 답 |
|---|---|
| 앱 하나만 되나? | 아니다. 「전체 화면」을 고르면 거의 모든 앱 (통화 제외, 보호 콘텐츠 일부 ❓) |
| 어떻게 켜나? | SafeEar → 「측정 시작」 → 「전체 화면」 → 「공유 시작」. 확인은 매번 필요 |
| 어떻게 끄나? | 상단 캡처 표시 또는 앱에서. 재시작·앱 종료 시 자동으로 꺼짐 |
| 얼마나 자주 켜나? | 화면 잠금 실험 결과에 따라 **하루 한 번 ~ 화면을 켤 때마다** |
| 꺼져 있으면? | 크기 기반 핵심 기능은 그대로, 첨도·대역 지도는 추정 또는 공백 |
| 가장 먼저 할 일 | iOS 27 iPhone으로 **화면 잠금 상태 30분 캡처 실험** |
